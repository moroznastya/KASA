# PRRO `test-connection` — діагностика помилки -1 (2026-08-01)

## Симптом

`POST /api/v2/prro/test-connection` повертав:

```json
{"status": -1, "ok": false,
 "error": "Виникла помилка при розборі чи формуванні даних (пошкоджені дані чи невірний формат)"}
```

при налаштованому тестовому ключі `certs/prro-test/Key-6_test3.dat`
(пароль `tect3`, mode=test).

## Першопричина (встановлено експериментально)

Фіскальний сервер ДПС (cabinet.tax.gov.ua:9443) **вимагає у полі
`Check.check_sign` підписаний XML-документ СЗЗД**:

- Документація API (`docs/scr/_site_text.txt`):
  «Для перевірки зв'язку використовується метод ping (Check) який повертає
  CheckResponse та XML з типом `<CT="111">`. MAC не заповнюється.»
  та «Сформований XML-документ повинен бути підписаний та переданий в
  параметрі check_sign».
- Офіційний семпл ДПС (github.com/programika/prro_sample, `Sender.java`):
  `ping()` підписує XML через ІІТ SDK (`ee.SignInternal(...)`) і передає
  його в `check_sign`.

### Експерименти проти тестового API

| Варіант `check_sign`                          | Відповідь сервера                          |
|-----------------------------------------------|---------------------------------------------|
| порожній (старий код)                         | -1 ERROR_VEREFY (помилка розбору)          |
| непідписаний XML `<C T="111">`                | -1 ERROR_VEREFY (помилка розбору)          |
| XAdES-підписаний (self-signed RSA) XML        | -1 ERROR_VEREFY (підписант не розпізнаний) |
| XML T=111 + check_type=CHK + sendChkV2        | -4 ERROR_UNKNOWN (інший шлях — структура розпізнана) |

Висновок: **без валідного підпису зареєстрованого підписанта сервер завжди
повертає -1**. Це очікувана поведінка для не-зареєстрованого/нечитаємого КЕП.

## Блокер: формат ключа ІІТ «ЦСК-1»

`Key-6_test3.dat` (946 байт) — контейнер **ІІТ «ЦСК-1»** (OID
`1.3.6.1.4.1.19398.1.1.1.2`, ДСТУ 4145-2002):

```
SEQUENCE
├─ SEQUENCE
│  ├─ OID 1.3.6.1.4.1.19398.1.1.1.2   (ДСТУ 4145-2002)
│  └─ SEQUENCE { OCTET STRING S1, OCTET STRING S2 }
└─ OCTET STRING (908 байт, зашифровано)
```

Розшифрування виконує **закрите крипто-ядро ІІТ** (SDK `EUSign` / `EUSignJava`,
JNI до нативної бібліотеки). Відкритих Python-реалізацій немає; `cryptography`,
`pycryptodomex`, `gostcrypto` не підтримують ні контейнер, ні ДСТУ 4145.

**Вирішення для користувача:** конвертувати ключ у PKCS#12 (`.pfx/.p12`)
або PEM (KeyConverter / ПЗ «Користувач ЦСК-1» від ІІТ) і повторно
налаштувати ПРРО.

## Що виправлено

1. **`grpc_client.ping()`** — тепер приймає `check_sign` і передає XML
   службового чеку T=111 (раніше — порожній `b""`, що гарантовано давало -1).
   Додано debug-лог (`check_sign_len`).

2. **`date_time`** — переведено на формат `yyyyMMddHHmmss` (14 цифр)
   згідно з офіційним семплом ДПС (`Sender.java`), а не Unix epoch.

3. **`crypto_signer`** — детекція контейнера ІІТ «ЦСК-1» (OID 19398) зі
   зрозумілою помилкою замість плутаного `Could not deserialize PKCS12 data`.

4. **`test_connection()`** — формує XML T=111, намагається підписати КЕП,
   надсилає на сервер і повертає:
   - `status` — реальний статус сервера;
   - `error` — багаточастинне пояснення (проблема КЕП + відповідь сервера
     + людською мовою розшифровка коду статусу: -13 ПРРО не зареєстровано,
     -14 підписант не зареєстрований, -15 зміна не відкрита тощо).

## Результат після виправлення

```json
{"status": -1, "ok": false,
 "error": "КЕП не вдалося використати: Файл ключа є контейнером ІІТ «ЦСК-1»
           (Key-6.dat, ДСТУ 4145-2002)... | Відповідь сервера: Виникла помилка
           при розборі... | Помилка перевірки підпису/розбору XML (ERROR_VEREFY)..."}
```

Статус **-1 є очікуваним**, доки:
1. ключ КЕП не буде прочитано (ІІТ → конвертація в PKCS#12/PEM), або
2. сертифікат підписанта не буде зареєстровано в тестовому середовищі ДПС.

Як тільки ключ стане читаємим — `test_connection` поверне статус сервера
(очікувано -13 ERROR_NOT_REGISTERED_RRO або -14 ERROR_NOT_REGISTERED_SIGNER,
доки ПРРО/підписант не зареєстровані, або 1 OK після реєстрації).

## Оновлення: JKS-ключ ПриватБанку (2026-08-01, 18:30)

Користувач замінив ключ на `certs/prro-test/pb_3791505547 (2).jks` (пароль `test2003`).

### Що встановлено

- **JKS містить ключ ДСТУ 4145-2002** (OID `1.2.804.2.1.1.1.1.3.1.1`, little endian,
  крива №6, ІІТ-формат атрибутів `1.3.6.1.4.1.19398.1.1.2.*`), сертифікат ЗЦ НБУ.
  Це **стандартний тестовий ключ ПриватБанку для ПРРО**.
- cryptography **не підтримує** ДСТУ 4145-2002 (`Unknown key type`).
- pyjks 20.0.0 падає при `decrypt()` на PKCS#8 з ДСТУ-параметрами
  (pyasn1 rfc5208 не розуміє AlgorithmIdentifier) — **обхід реалізовано**
  (ручний розбір DER, monkeypatch decrypt у `crypto_signer._load_from_jks`).

### Блокер

`crypto_signer.sign()` будує **RSA-SHA256 XAdES** (signxml) — ДПС для СЗЗД
приймає лише **ДСТУ 4145-2002 + ГОСТ 34311 (ДСТУ 7564:2014)**. Тому:

- будь-який український КЕП (ІІТ, ПриватБанк, «Україна») НЕ підпишеться
  поточним модулем;
- потрібна реалізація **ДСТУ 4145 крипто-ядра** (шляхи нижче).

### Шляхи реалізації ДСТУ 4145 (для наступного етапу)

1. **ІІТ SDK EUSign** (офіційне крипто-ядро, ctypes; deb з iit.com.ua) — найнадійніше.
2. **gost-engine** (`libengine-gost-openssl` 3.0.2 з Ubuntu noble) — НЕ працює
   з OpenSSL 3.0.13 (провайдер активується, але алгоритми не реєструються).
3. **Чисті Python-реалізації** ДСТУ 4145 — на PyPI відсутні (dstu4145 не існує),
   gostcrypto — це російський ГОСТ, не ДСТУ.
4. Хеш ДСТУ 7564:2014 (Стрибог 256) — доступний у `gostcrypto.hash` (ГОСТ Р 34.11-2012).
5. XAdES `DSTU4145WithGOST34311` — signxml не вміє, потрібна кастомна побудова
   (canonical C14N + підпис SignedInfo).
