## 3. Висновок 1: алгоритм MAC

**Поточна реалізація (Rust `compute_mac` = Python `compute_mac`, 1:1):**

```
MAC = Base64(SHA-256(канонічний <DAT>))     // 32 байти → 44 символи + '='
```

**Відповідність [СЗЗД]:**
- «Тег `<MAC>` містить в собі значення MAC відповідного пакету даних, попередньо
  перетворений в формат Base64. MAC обчислюється для тегу `<DAT>` з усім його
  вмістом» — ✅ наша реалізація обчислює MAC саме від канонічного `<DAT>` і
  кодує в Base64.
- Канонічний вигляд `<DAT>` реалізовано 1:1 (СЗЗД, Додаток: видалення пробілів,
  алфавітний порядок атрибутів) — підтверджено golden-тестами parity
  (`golden_xml.rs`, `TestHashChainB1`).

**Обмеження (зафіксовано чесно):**
- Конкретний криптографічний алгоритм ПРРО-MAC (SHA-256? ГОСТ? інший) у
  доступних джерелах **публічно не документований**: [СЗЗД] для РРО каже
  «залежить від моделі РРО», для ПРРО ДПС у [ДПС] формула не наведена.
- Офіційного семпла `Sender.java` у репозиторії **немає**.
- Приклад MAC у [ДПС] §5 (`001A0000...A2D6`, 56 hex) **не збігається** ні з
  SHA-256-hex (64), ні з SHA-256-base64 (44+1). Можливі пояснення: демонстраційне
  значення, інший алгоритм, або урізаний хеш.
- **Рекомендація:** підтвердити алгоритм smoke-тестом на тестовому API
  (`cabinet.tax.gov.ua:9443`) — відправка чека з нашим MAC і перевірка статусу
  (не `ERROR_BAD_MAC`). Доступ до test API в цій сесії відсутній.

## 4. Висновок 2: QR `mac` — ВИПРАВЛЕНО (був баг)

**[ДПС] §5:** для перевірки чеку використовується
`https://cabinet.tax.gov.ua/cashregs/check?mac=<MAC hash>&date=yyyyMMdd&time=HHmm&id=<ід чеку>&sm=<сума>&fn=<ФН>`,
де `mac` — **MAC (hash)** чека.

**Баг:** до Фази 7 в обох реалізаціях у QR передавався `id_sign` (серійний номер
підпису КЕП), а НЕ MAC чека:

```rust
// БУЛО (Rust):  build_fiscal_check_url(..., Some(&serial));       // serial = id_sign
// СТАЛО (Rust): build_fiscal_check_url(..., Some(mac));            // mac = compute_mac(dat_xml)
# Python:       mac=serial  →  mac=mac
```

**Виправлення (Rust + Python синхронно, 1:1):**
- `src/prro/fiscalize.rs` / `fiscalize_receipt_use_case.py`: QR будується з
  `mac` (MAC чека), не з `serial` (id_sign).
- `src/prro/settings.rs` / `qr_url.py`: параметри URL-кодуються 1:1
  (`urlencode_plus` == Python `urllib.parse.urlencode`); base64 MAC містить
  `+ / =` → `%2B %2F %3D` — усунуто розбіжність parity, виявлену тестом.

**Формат QR-URL (після виправлення, відповідає [ДПС]):**
```
https://cabinet.tax.gov.ua/cashregs/check?mac=<MAC>&date=YYYYMMDD&time=HHmm&id=<fiscal_id>&sm=<sum.2>&fn=<prro_fn>
```

## 6. Відкриті питання (передано координатору)

1. Точний криптоалгоритм ПРРО-MAC — потребує підтвердження на test API.
2. Приклад MAC у [ДПС] (56 hex) не збігається з SHA-256 — уточнити у ДПС/інтегратора.
3. QR `sm` — сума з роздільником "." (підтверджено [ДПС]); локальна валідація — ок.
