> Статус: ПРОПОЗИЦІЯ (аналіз, без реалізації)
> Дата: 2026-08-20
> Стек: Rust-фасад (torgashka-*) + React + PostgreSQL

---

## 1. ІНКАСАЦІЇ ТА ВНЕСЕННЯ КОШТІВ

### 1.1 Поточний стан

- Чеки зберігають `cash_amount` / `card_amount` / `payment_method` / `paid_amount` / `change_amount` — **є суми готівкових продажів, але немає обліку каси** (балансу, руху готівки).
- Є `work_sessions` (вхід/вихід касира) — це логін-сесія, **не зміна каси**.
- ПРРО-зміни (`prro_shifts`) — фіскальні зміни, не касова дисципліна.
- Немає жодної таблиці "каса" чи "готівкова операція".

### 1.2 Що пропонується

Новий модуль **«Каса / Готівкові операції»** (Cash Operations):

**Нові таблиці:**

```
cash_registers           — каси (фізичні/логічні грошові ящики)
  id, store_id FK, name, is_active, created_at

cash_register_shifts      — зміни каси (відкриття/закриття)
  id, register_id FK, user_id FK, opened_at, closed_at,
  opening_balance, closing_balance, expected_balance, is_closed

cash_operations           — рух готівки (внесення/вилучення/інкасація/розмін)
  id, store_id FK, register_id FK, shift_id FK, user_id FK,
  operation_type ENUM('deposit','withdrawal','collection','exchange_in','exchange_out'),
  amount NUMERIC(12,2),
  balance_after NUMERIC(12,2),       -- баланс каси після операції
  comment, created_at
```

**Бізнес-логіка:**

- Баланс каси = `opening_balance` + Σ готівкових продажів за зміну
  + `deposit` − `withdrawal` − `collection` − `change_amount` (здачі) − `exchange_out` + `exchange_in`.
- **Інкасація** = вилучення виручки з каси (тип `collection`) із зазначенням суми та, за потреби, реквізитів інкасації (номер, сума в інкасаторській сумці). Сума інкасації не може перевищувати поточний баланс.
- **Внесення коштів** = `deposit` (розмінна монета/стартовий капітал на початок зміни, або поповнення протягом зміни).
- **Розмін** = `exchange_in`/`exchange_out` (розмін дрібних грошей) — опційно, якщо потрібно.
- Кожна операція — **атомарна транзакція** з перерахунком `balance_after`, блокуванням рядка каси (`SELECT ... FOR UPDATE`), щоб уникнути гонок двох касирів.

**Куди в програмі:**

- **POS-сторінка** (`PosPage.tsx`): кнопки «Внесення» та «Інкасація» на панелі оплати/знизу екрана. Доступні адміну та касиру (за пермішеном).
- **Новий пункт меню «Каса»** (sidebar): історія операцій, відкриття/закриття зміни, звіт «Каса за зміну» (Z-подібний: продажі готівкою/карткою, внесення, інкасації, очікуваний залишок).
- **Звіти** (`ReportsPage.tsx`): касова книга за період, сумарна інкасація за день/місяць.
- **Налаштування**: ліміт-попередження (наприклад, попереджати про інкасацію при сумі > N грн) — через існуючу `system_settings`.

**Ролі/пермішени** (розширити існуючу модель permissions JSONB):
`cash.view`, `cash.deposit`, `cash.collect`, `cash.close_shift`, `cash.open_shift`.

**Чому саме так:** модуль лягає поруч із `work_sessions` та `prro_shifts`, використовує вже наявні `cash_amount` з чеків (не дублює облік продажів), дає повну історію руху готівки для інвентаризації каси.

## 2. РОЗМЕЖУВАННЯ ДАНИХ ЗА ТОРГОВЕЛЬНИМИ ТОЧКАМИ

### 2.1 Варіанти архітектури

| Варіант | Опис | Плюси | Мінуси | Висновок |
|---|---|---|---|---|
| **A. Окрема БД на точку** | кожна точка = окрема PostgreSQL БД | повна ізоляція, простий бек-ап | неможливі міжточкові запити, міграції × N БД, складна оркестрація підключень | ❌ відхилено |
| **B. Одна БД, окрема schema на точку** | PostgreSQL schemas + `search_path` | ізоляція на рівні СКБД | міжточкові запити вимагають перемикання схем, міграції × N схем, ускладнення пулу з'єднань | ⚠️ надмірно для цього масштабу |
| **C. Одна БД, колонка `store_id`** | мульти-тенант: `store_id` FK у кожній бізнес-таблиці + RLS | міжточкові запити тривіальні, одна схема, стандартний патерн | вимагає дисципліни: кожен запит фільтрується по `store_id` | ✅ **рекомендовано** |

**Рекомендація: C** — одна БД, колонка `store_id` на всіх бізнес-таблицях, плюс **Row-Level Security (RLS)** у PostgreSQL як захисний другий контур (навіть якщо десь забули фільтр — СКБД не віддасть чужі дані).

### 2.2 Зміни схеми

**Нова таблиця:**
```
stores
  id UUID PK, name, address, phone, is_active BOOL,
  created_at, updated_at
```

**Додати `store_id` (NOT NULL після backfill) до:**
`products`, `barcodes`, `categories`, `receipts`, `receipt_items`, `invoices`,
`invoice_items`, `transfers`, `write_offs`, `return_invoices`, `purchase_orders`,
`inventories`, `debtors`, `debtor_payments`, `supplier_products`,
`work_sessions`, `prro_settings`, `prro_shifts`, `prro_queue_items`,
`print_templates`, `system_settings`, `cash_registers`, `cash_operations`.

**Довідники — рішення про спільність:**
- `suppliers` (постачальники) — **спільні** (один постачальник обслуговує багато точок). Зв'язок точка↔постачальник — через `supplier_products` та накладні (там `store_id`).
- `categories` — **на точку** (дерево категорій своє) або спільні з прапорцем видимості. Перший крок: на точку, простіше.
- `users` — користувач не прив'язаний жорстко до однієї точки. Зв'язок через нову таблицю:
  ```
  user_stores
    user_id FK, store_id FK, role ENUM('admin','cashier'), permissions JSONB,
    is_default BOOL, PK(user_id, store_id)
  ```
  Це дозволяє одному власнику керувати кількома точками, а касиру бути прив'язаним до однієї. Пермішени стають **на рівні точки** (роль/права у `user_stores`, а не в `users`).

**Індекси:** композитні `(store_id, created_at)`, `(store_id, <бізнес-ключ>)` на всіх гарячих шляхах (пошук товару за ШК у межах точки — критично для POS).

### 2.3 Стратегія міграції

1. Створити `stores` + таблицю `user_stores` (та `cash_registers`, `cash_operations`).
2. Seed: точка **«Основна точка»** (або з налаштування `shop_name` — уже є в Settings) → всі існуючі дані отримують `store_id = <основна точка>`.
3. Додати колонки `store_id` як NULLABLE → backfill → ALTER SET NOT NULL.
4. Увімкнути RLS: `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` + політика `store_id = current_setting('app.store_id')`.
5. Перенести `role`/`permissions` з `users` у `user_stores` (зберегти зворотну сумісність на час перехідного періоду).

## 3. ПЕРЕМИКАННЯ МІЖ ТОЧКАМИ + МІЖТОЧКОВА ВИДИМІСТЬ

### 3.1 Перемикання активної точки (власник)

**Backend (Rust, torgashka-api):**
- Авторизація (`auth.rs`) повертає список точок користувача + `default_store_id`.
- Middleware/extractor `StoreContext`: читає заголовок **`X-Store-Id`** з кожного запиту → валідує доступ користувача до точки (через `user_stores`) → кладе `store_id` у контекст запиту.
- Всі use cases отримують `store_id` з контексту — **жоден запит не може бути без точки** (окрім системних: сам список точок).
- Кеш (Redis) — ключі з префіксом `store:{store_id}:...`, щоб перемикання не змішувало дані.

**Frontend (React):**
- Список точок приходить при логіні → зберігається в `authStore`.
- **Switcher точок у Header** (`Header.tsx`): dropdown «Поточна точка: ▾». Вибір → зміна `activeStoreId` у Zustand → усі API-сервіси автоматично додають `X-Store-Id` (інтерцептор axios) → перезавантаження даних сторінки.
- Обмеження: касир бачить лише ті точки, де він є у `user_stores`; власник — всі.
- При вході — автовибір `default_store_id`.

### 3.2 Міжточкова видимість товарів (один магазин бачить товар іншого)

**Спосіб: read-only «глобальний пошук залишків».**

- Нова read-only модель/в'юха:
  ```
  store_inventory (view)
    store_id, store_name, product_id, product_title, barcode,
    price, stock, updated_at
  ```
  Джерело: `products` + `stock` (або поточне поле `stock` на продукті, якщо склад на рівні продукту).
- **Новий ендпоінт:** `GET /api/v1/stores/{id}/inventory?query=...&barcode=...` — пошук товару в конкретній іншій точці. Права: `inventory.view_other_stores` (за замовчуванням — тільки адмін/власник).
- **UI:** у `ProductListPage` та на POS-екрані пошуку товару — кнопка/блок «Наявність в інших точках»: таблиця (точка, ціна, залишок). Тільки перегляд, без редагування.
- **Опційно (наступний крок):** із цього ж екрана створити `Transfer` між точками (переміщення) — існуюча модель `transfers` має `from_location`/`to_location` (зараз рядки) → апгрейд до `from_store_id`/`to_store_id` FK. Це дає повний цикл: побачив залишок в іншій точці → замовив переміщення → склад зменшився/збільшився.

### 3.3 Обмеження та ризики

- Офлайн-режим (Tauri): локальний SQLite (`torgashka-infrastructure/src/offline/db.rs`) зараз тримає products/receipts/settings — потрібно додати `store_id` і в офлайн-схему, щоб черга синхронізації не перемішувала точки.
- Робота зміни касира та інкасації прив'язані до точки: відкрив зміну в точці A → інкасація/продажі йдуть у точку A; перемикання на точку B вимагає закриття/окремої зміни.
- ПРРО: ключі/налаштування ПРРО вже залежні від точки (фіскальний номер точки) — `prro_settings` отримує `store_id` і стає per-store.

## 4. ПОРЯДОК ВПРОВАДЖЕННЯ (етапи)

1. **Етап 1 — фундамент мультиточковості:** `stores`, `user_stores`, міграція `store_id` + backfill + RLS, StoreContext у Rust-фасаді, `X-Store-Id` у фронті, switcher у Header.
2. **Етап 2 — міжточкова видимість:** view `store_inventory`, ендпоінт пошуку, UI «наявність в інших точках», апгрейд `transfers` на `store_id`.
3. **Етап 3 — касові операції:** `cash_registers`, `cash_register_shifts`, `cash_operations`, логіка балансу, кнопки в POS, сторінка «Каса», звіти, пермішени.
4. **Етап 4 — офлайн:** `store_id` в офлайн-схемі, синхронізація черги з урахуванням точки.

Кожен етап завершується: міграція БД + Rust-тести фасаду + differential-тести (там, де є legacy-еталон) + ручна перевірка UI.

## 5. UX — ЯК ЦЕ ВИГЛЯДАЄ ЗІ СТОРОНИ КОРИСТУВАЧА

> Сценарії описані з позиції двох ролей: **касир** (працює за касою) та
> **власник/адмін** (керує мережею). Усі дії — у тому самому React-застосунку.

### 5.1 Вхід у систему (зміна ролей)

**Касир Олег** відкриває застосунок → екран входу (PIN-клавіатура або логін/пароль).
Після входу:
- Якщо касир прив'язаний до **однієї** точки — система одразу відкриває її,
  селектор точок у шапці **не показується** (нема чого перемикати).
- Якщо касир має доступ до кількох точок (рідко) — у шапці з'являється
  перемикач, і система відкриває точку з прапорцем `is_default`.

**Власник Ірина** входить і бачить у шапці справа:
```
[🏬 Основна точка ▾]  [👤 Ірина]
```
Натискає на назву точки → випадає список усіх її точок з адресами:
```
┌─────────────────────────────┐
│ 🏬 Основна точка            │ ← активна (галочка)
│    вул. Хрещатик, 1         │
│ 🏬 Філія на Лівому березі   │
│    вул. Броварська, 15      │
│ 🏬 Склад-магазин            │
│    вул. Промислова, 3       │
└─────────────────────────────┘
```
Вибирає «Філія на Лівому березі» → сторінка миттєво перезавантажує дані:
шапка показує «Філія на Лівому березі», усі списки (товари, чеки, звіти) —
вже з даними філії. Перемикання займає < 1 сек.

### 5.2 Робочий день касира (готівкові операції)

**08:55. Початок зміни.**
Олег натискає в POS-екрані кнопку **«Відкрити зміну»** → модальне вікно:
```
┌──────────────────────────────────────┐
│  Відкриття зміни                     │
│  Каса:        [Каса №1 ▾]            │
│  Початковий залишок: [ 500.00 ] грн  │  ← розмінна монета
│  Коментар (опц.): [________________] │
│        [Скасувати]    [Відкрити зміну]│
└──────────────────────────────────────┘
```
Після відкриття у верхній частині POS-екрана з'являється панель стану каси:
```
Зміна №12 відкрита · Касир: Олег · Готівка в касі: 500.00 грн
```
Ця панель видно **завжди** — касир бачить поточний баланс у реальному часі.

**12:30. Внесення розмінної монети.**
Закінчилися дрібні гроші. Олег натискає **«Внесення»** → модалка:
```
┌──────────────────────────────────────┐
│  Внесення коштів у касу              │
│  Сума:        [ 200.00 ] грн         │
│  Причина:     [Розмінна монета ▾]    │  ← розмін/поповнення/інше
│  Коментар:    [________________]     │
│  Баланс після операції: 700.00 грн   │  ← живий перерахунок
│        [Скасувати]       [Внести]    │
└──────────────────────────────────────┘
```
Після підтвердження баланс у панелі оновлюється: `700.00 грн`.

**18:00. Інкасація виручки.**
У касі накопичилось 15 200 грн. Олег (або адмін) натискає **«Інкасація»**:
```
┌──────────────────────────────────────┐
│  Інкасація                           │
│  Сума до вилучення: [ 15000.00 ] грн │
│  Номер сумки:       [ 00042 ]        │
│  Коментар:          [Щоденна інкасація]│
│  Залишиться в касі: 200.00 грн       │  ← живий перерахунок
│        [Скасувати]      [Інкасувати] │
└──────────────────────────────────────┘
```
- Якщо сума більша за баланс — кнопка блокується, червоним підказка
  «Недостатньо готівки в касі».
- Після підтвердження: друк/екран **акта інкасації** (сума, номер сумки,
  час, касир, підпис) → панель балансу оновлюється: `200.00 грн`.

**21:00. Закриття зміни.**
Олег натискає **«Закрити зміну»** → система показує **звіт каси за зміну**:
```
ЗВІТ КАСИ №12 — 2026-08-20
Каса №1 · Касир: Олег · Філія на Лівому березі
─────────────────────────────────────
Початковий залишок ......... 500.00
Продажі готівкою ........... 14 800.00
Продажі карткою ............ 6 200.00   ← тільки інформаційно
Здача (change) ............. -120.00
Внесення ................... +200.00
Інкасації .................. -15 000.00
─────────────────────────────────────
ОЧІКУВАНИЙ ЗАЛИШОК .......... 380.00
ФАКТИЧНИЙ ЗАЛИШОК ........... [ 380.00 ] ← касир перераховує готівку
  [Розбіжність]  [Закрити зміну]
```
- Якщо фактичний збігається з очікуваним — зміна закривається, звіт можна
  роздрукувати.
- Якщо є розбіжність — касир зобов'язаний ввести фактичну суму; різниця
  фіксується в звіті (для адміна це видно в історії змін).

### 5.3 Що бачить власник у модулі «Каса»

Новий пункт меню **«Каса»** (доступний адміну; касиру — тільки «своя каса»):

- **Список кас** (по точках): назва, точка, статус (відкрита зміна/закрита),
  поточний баланс, хто відкрив.
- **Історія операцій**: таблиця (дата, каса, тип [внесення/інкасація/...],
  сума, баланс після, касир, коментар) з фільтрами за точкою/періодом/типом.
- **Історія змін**: коли відкрита, коли закрита, очікуваний/фактичний залишок,
  розбіжності — по кожній зміні кожної каси.
- **Друк**: касова книга за день, акт інкасації, звіт за зміну.

У **«Звітах»** з'являються:
- «Каса: рух готівки за період» (графік + таблиця: внесення/інкасації/залишок),
- «Інкасації за місяць» (сумарно по точках — скільки виручки зібрано де).

### 5.4 Міжточкова видимість товарів (власник/адмін)

**Сценарій:** у «Основній точці» клієнт питає товар, якого немає в наявності.
Адмін відкриває картку товару (або шукає його) і бачить блок:
```
Наявність в інших точках:
┌────────────────────────────┬──────────┬────────┐
│ Точка                      │ Ціна     │ Залишок│
├────────────────────────────┼──────────┼────────┤
│ Філія на Лівому березі     │ 89.00    │ 12 шт  │
│ Склад-магазин              │ 92.00    │ 3 шт   │
└────────────────────────────┴──────────┴────────┘
[Створити переміщення з Філії]  ← опційно, наступний крок
```
Той самий блок доступний на **POS-екрані**: касир сканує ШК товару, якого
немає, система показує «Немає в наявності» + список точок, де товар є —
касир може одразу сказати клієнту, де він є, або (з правами) замовити
переміщення. Це **read-only** — касир не може редагувати залишки іншої точки.

### 5.5 Обмеження, які бачить користувач

- **Перемикання точки під час відкритої зміни каси** — заборонено з
  попередженням: «Спочатку закрийте зміну каси». Касир фізично не може
  «випадково» почати продавати в іншій точці з чеком зі своєї зміни.
- **Офлайн-режим**: якщо інтернет зник, касир продовжує працювати в тій самій
  точці; при відновленні зв'язку черга синхронізується в точку, яка була
  активною на момент продажу (дані не змішуються між точками).
- **Права**: кнопки «Внесення/Інкасація» неактивні, якщо у користувача немає
  відповідного пермішена — інтерфейс не показує недоступні дії.

### 5.6 Підсумок: користувацькі сценарії (checklist для приймальних тестів)

| # | Сценарій | Очікуваний результат |
|---|---|---|
| 1 | Касир відкриває зміну з 500 грн | Панель «Готівка в касі: 500.00» |
| 2 | Касир вносить 200 грн | Баланс 700.00, операція в історії |
| 3 | Касир інкасує 15 000 грн | Баланс 200.00, акт інкасації з номером сумки |
| 4 | Касир намагається інкасувати більше балансу | Кнопка заблокована + підказка |
| 5 | Касир закриває зміну, суми збігаються | Звіт, зміна закрита |
| 6 | Касир закриває зміну, суми не збігаються | Розбіжність зафіксована, видно адміну |
| 7 | Власник перемикає точку в шапці | Усі дані сторінки — нової точки, < 1 сек |
| 8 | Касир з однією точкою | Селектор точок не показується |
| 9 | Адмін дивиться «Наявність в інших точках» | Таблиця точок: ціна + залишок, тільки перегляд |
| 10 | Касир без права інкасації | Кнопка «Інкасація» неактивна/невидима |
| 11 | Касир намагається перемкнути точку з відкритою зміною | Блокування з поясненням |
| 12 | Офлайн-продажі синхронізуються | Дані потрапляють у точку продажу, без змішування |
