## 0. Контекст

**Мета:** Реалізувати ПРРО для фіскалізації чеків — програмний РРО, що реєструє
розрахункові операції (чеки продажу/повернення) та передає їх до ДПС України
(фіскальний сервер) з ЕЦП-підписом (XAdES), за протоколами ДПС.

**Джерела (kasa/docs/scr/):**
- `site.html` — «Опис API Електронного кабінету» (cabinet.tax.gov.ua/help/api.html).
  Містить розділ «Фіскалізація чеків та передача Z-звітів в рамках експериментального
  проекту» + опис тестового API («Z-звіти на тестове API не є фіскальними»).
- `SZZD_RRO_Protokol_peredach_nformats_2_1_7.doc` — протокол передачі інформації
  (формат 2.1.7), 43 стор., Word 97-2003 (бінарний .doc, cp1251).

**Режими роботи:** спочатку ТЕСТОВЕ API ДПС (відшліфувати), потім БОЙОВЕ.

**Вимоги користувача:**
1. ПРРО виконує всі необхідні операції фіскалізації чеків, що вимагає ДПС.
2. Інтеграція з Torgashka: вікно роботи з ПРРО (операції), налаштування ПРРО
   (електронний ключ + пароль), фіскалізація ЛИШЕ товару, який прийшов
   по фіскальній накладній (оприбуткований товар).

## 1. Поточний стан Torgashka (що вже є / чого немає)

### Є (готова база для інтеграції):
- ✅ Чеки продажу/повернення: `Receipt` (ReceiptType: sale/return; ReceiptPaymentMethod:
  cash/card/mixed; original_receipt_id для повернень), CRUD API (`api/v1/receipts`),
  статистика (`/stats/today`, `/search`, `/by-product`).
- ✅ Робочі зміни: `api/v1/work_sessions` (`/my`, `/report`) — база для змін ПРРО.
- ✅ Модульна система налаштувань: `api/v1/settings` (GET/PUT module, key) —
  ідеальна для зберігання параметрів ПРРО (module="prro").
- ✅ Вхідні накладні (прихід товару): `invoices`, інвентаризація — основа правила
  «товар оприбуткований».
- ✅ Друк: `print` + Tauri — для друку фіскальних чеків.
- ✅ POS-екран: `frontend/src/pages/pos/PosPage.tsx` — місце кнопки «Фіскалізувати».
  ⚠️ Поруч лежить `PosPage.tsx.bak` — перевірити перед інтеграцією (можлива
  незавершена робота).

### Немає (треба створити):
- ❌ ПРРО-модуль у backend (клієнт фіскального сервера ДПС, криптосервіс ЕЦП/XAdES).
- ❌ Фіскальні поля в чеках (fiscal_number, fiscal_date, fiscal_sign, статус).
- ❌ Модель змін ПРРО (PrroShift / розширення work_sessions).
- ❌ Вікно ПРРО та налаштування ПРРО у frontend.
- ❌ Валідація «товар оприбуткований по фіскальній накладній» перед фіскалізацією.

## 2. Архітектурні рішення (попередньо, деталі — в ADR)

- Модуль у Clean Architecture (як існуючі): `api/v2/prro.py` + `application/use_cases/prro_use_cases.py`
  + `application/dto/prro_dto.py` + `contracts/prro_contract.py` + `infrastructure/services/`.
- `infrastructure/services/prro_client.py` — HTTP-клієнт фіскального сервера ДПС
  (тестовий/бойовий URL, TLS, ретраї, JSON за протоколом 2.1.7).
- `infrastructure/services/prro_crypto.py` — ЕЦП: читання ключа (формати АЦСК),
  XAdES-підпис (signxml/cryptography), перевірка.
- Налаштування: `system_settings` module="prro" (шлях до ключа, пароль [шифровано],
  режим test/prod, URL сервера, фіскальний номер ПРРО).
- Чек: додати фіскальні поля + зв'язок зі зміною ПРРО; статуси фіскалізації
  (pending → fiscalized / error).
- Офлайн: чеки у статусі pending → фонова синхронізація при відновленні зв'язку
  (відповідно до вимог ДПС, уточнити в протоколі).

## 4. Ризики та відкриті питання

1. **Протокол 2.1.7** — бінарний .doc (Word 97-2003, cp1251); catdoc/antiword/libreoffice
   не встановлені → потрібна конвертація (python olefile / встановити antiword).
2. **Тестове API ДПС** — Z-звіти не фіскальні (очікувано); можливі ліміти/обмеження.
3. **ЕЦП** — формати ключів АЦСК (pfx/jks/Key-6.dat), вимоги XAdES (BES/EPES),
   сумісність бібліотек signxml/cryptography — перевірити на Фазі 0.
4. **Офлайн** — граничні терміни передачі даних згідно з ДПС (уточнити в протоколі).
5. **Безпека** — пароль ключа не зберігати у відкритому вигляді (шифрування).
6. **PosPage.tsx.bak** — перевірити, чи POS-екран у робочому стані перед інтеграцією.
7. **Правило «товар з фіскальної накладної»** — УТОЧНИТИ з користувачем:
   (а) блокувати продаж неоприбуткованого товару чи (б) лише попереджати/позначати.
