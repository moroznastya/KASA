## 0. TL;DR для чергового

### 0.1 Модель топології — SSOT (РІШЕННЯ ТВОРЦЯ 13.09.2026)

> **«Кожен пристрій напряму взаємодіє з БД ZBOX для синхронізації даних, і має
> копію локально БД, з якою взаємодіє.»** — рішення Творця **13.09.2026** (SSOT,
> не інтерпретується). Оформлено як [ADR-0009](../adr/ADR-0009-direct-db-sync-model.md).

Практично:

* **Джерело даних — БД на ZBOX** (`10.179.55.210:5432`, `database=pos_system`,
  `user=postgres`): пристрій підключається до неї **напряму**, тим самим
  PostgreSQL-протоколом, без будь-якого проміжного HTTP-сервісу.
* **Локальна копія БД — на кожному пристрої** (вбудований PostgreSQL застосунку;
  `data_dir`/порт — §15.0(d)).
* **На ZBOX HTTP-фасаду НЕМАЄ і він не потрібен.** Перевірено на живій системі
  **13.09.2026** з робочої машини `10.179.55.165`: порт **`5432` — ВІДКРИТИЙ**,
  порти **`8000`, `80`, `443` — ЗАКРИТІ**. Отже «адреса хаба `:8000`»,
  `GET /api/v1/sync/snapshot` по мережі та майстер `/node-join` у цій топології
  недосяжні за визначенням (§15.0, §15.6).
* Кожен застосунок піднімає **власний** локальний HTTP-шар на loopback
  (`127.0.0.1:8000`) для власного UI — це не «хаб» і мережевою точкою входу
  він не є.

**Розбіжність версій PG і наслідок для синку** (підтверджено Творцем/NIKO 2026-09-13):

| | Версія | Джерело |
|---|---|---|
| БД ZBOX (джерело даних) | **PostgreSQL 14.24** | Творець/NIKO 2026-09-13 (з цієї машини **не** перевірялося — ⏳) |
| Локальна копія (пристрій) | **PostgreSQL 17** (на цій машині — 17.6) | cmdline процесу: `/usr/lib/postgresql/17/bin/postgres -D /home/anastasia/torgashka_pg_primary -p 5544` |

**Наслідок:** фізична потокова реплікація між різними major-версіями (**14 → 17**)
**неможлива** — `pg_basebackup`, `primary_conninfo` і слоти реплікації в цій схемі
**не застосовні**, жодних механізмів `wal_level=replica` між ZBOX і пристроєм
**не будуємо**. Синхронізація виконується **на рівні застосунку** (протокол —
`docs/design/sync-schema-design.md`). Рудименти реплікації на локальному кластері —
⏳ §15.6-D. Не плутати: `artifacts/hub_snapshot/MANIFEST.md` («PostgreSQL 17.6») —
це знімок **локального** кластера, не ZBOX.

### 0.2 🔒 Шифрування каналу ZBOX ↔ пристрій — ⏳ ОЧІКУЄ РІШЕННЯ ТВОРЦЯ

Факт (ZBOX, надано координатором 13.09.2026; перевірено тут частково):
`pg_hba.conf` → `host all all 0.0.0.0 scram-sha-256`; `ssl = off`. Перевірка TLS
з робочої машини 13.09.2026: рукостискання не проходить (`openssl s_client
-connect 10.179.55.210:5432` → `write:errno=104`, з'єднання скинуто) —
узгоджується з `ssl = off`.

Наслідок: пароль (SCRAM) і **дані** йдуть без TLS. У межах закритого оверлею
(ZeroTier) це прийнятно як тимчасовий стан; **поза ZeroTier — неприйнятно**:
SCRAM захищає пароль від розкриття, але не дані. Окремо: `0.0.0.0` у `pg_hba`
означає, що до `:5432` може підключитися **будь-який** хост, який має мережевий
доступ (зараз його дає ZeroTier).

Варіанти (рішення — за Творцем, тут **не** ухвалюється):

1. **TLS на ZBOX** — `ssl = on` + сертифікат, клієнт із `sslmode=require`;
2. **Лише ZeroTier** — без TLS, але тоді обов'язково звузити `pg_hba` з `0.0.0.0`
   до ZeroTier-підмережі й не мати жодного пробросу `5432` назовні;
3. комбінація (TLS **і** `pg_hba` по ZeroTier-підмережі).

⏳ Питання до Творця: (а) TLS на ZBOX чи «лише ZeroTier»; (б) звужуємо `pg_hba`
з `0.0.0.0` до ZeroTier-підмережі; (в) якщо TLS — хто видає сертифікат
(self-signed із фіксацією відпечатка vs CA).

> 📘 Те саме питання зафіксовано в операторській інструкції:
> [onboarding-windows-device.md](./onboarding-windows-device.md) (рядок «TLS до ZBOX
> → `ssl=off`»). Обидва місця ведуть до **одного** ⏳ рішення (вище) — узгоджено
> 13.09.2026, щоб питання не жило в двох неузгоджених формулюваннях.

> Нижче (пп. 1–4) — **TL;DR HTTP-моделі** (ADR-0008), чинний лише для випадку
> «хаб — окремий HTTP-сервіс». Для топології ZBOX див. §0.1 і §15.0.

1. **Кожен магазин — повноцінна read-write PostgreSQL.** Жодного режиму «standby»,
   жодного «вузол не може писати», жодного promote. Концепцію «чи можу я писати»
   видалено разом із кодом (E7, коміт `50eb8ec`).
2. **Хаб** — окрема завжди-ввімкнена БД. Він **не** керує записом у магазинах:
   він приймає дані з вузлів (↑), роздає спільні довідники (↓) і арбітрує
   правки спільних сутностей.
3. **Недоступність хаба не зупиняє магазин.** Вузол пише локально, черга
   форвардингу росте; коли хаб піднявся — дані доїжджають (дублікатів немає).
4. **Ознака здоров'я:** `GET /api/v1/sync/status` → `queue.pending = 0`,
   `conflicts.open = 0`, `lag_seconds` малий.

## 1. Ролі інстанса

Роль **не налаштовується окремим перемикачем** — вона випливає з наявності
апстріму у власній БД інстанса:

| Роль | Ознака | Поведінка |
|---|---|---|
| **Вузол** (магазин) | у власній БД є налаштування `sync.hub_url` | пише локально; форвардить прийняте вгору (`hub_outbox`); тягне довідники pull-ом; надсилає пропозиції довідників |
| **Хаб** | `sync.hub_url` немає | приймає push від вузлів, виконує арбітраж, роздає довідники; сам не форвардить нічого |
| **Одиночна точка** | те саме, що «хаб» (немає апстріму) | працює автономно, як раніше; мережеві функції просто не задіяні |

Джерело істини ролі — **власна БД** (`sync.hub_url` / `sync.hub_token`), не
env-змінна: `torgashka-api/src/hub_forwarder.rs:20, 50-53, 70, 120`
(`HubForwardConfig::from_pool`), `torgashka-infrastructure/src/sync_settings.rs`.
Видно в API: `GET /api/v1/sync/status` → `role: "node" | "hub"`.

Заголовки скоупу: `X-Store-Id` (обов'язковий для sync-ендпоінтів вузла),
`X-Sync-Batch-Id` (штамп батча, `torgashka-api/src/sync.rs:738`),
`X-Schema-Major` (§9).

## 2. Два потоки даних

```
        ┌──────────────────────────── ХАБ (авторитет) ───────────────────────────┐
        │  приймає операційне (↑)   •   арбітрує спільні довідники   •  роздає (↓) │
        └───────▲───────────────────────────────────────────────┬────────────────┘
                │ push (форвардер, hub_outbox)                  │ pull (master, server_version)
        ┌───────┴───────────────┐                       ┌───────▼───────────────┐
        │ ВУЗОЛ A (магазин)     │                       │ ВУЗОЛ B (магазин)     │
        │ read-write PG         │                       │ read-write PG         │
        └───────▲───────────────┘                       └───────────────────────┘
                │ push каси (той самий ендпоінт)
        ┌───────┴───────────────┐
        │ КАСА (SQLite outbox)  │
        └───────────────────────┘
```

* **↑ Операційні дані** — факти магазину (чеки, накладні, рухи, борги,
  ПРРО-зміни тощо). Пише **лише той вузол, якому вони належать**.
* **↓ Спільні довідники** — те, що мусить бути однаковим у всіх точках
  (каталог, ціни, причини списання, шаблони…). Канонічну версію присвоює хаб.
* **Пропозиції** (`catalog_change_proposal`) — зустрічний потік для правок
  спільних сутностей: вузол просить, хаб вирішує (§6).

## 3. Push: вузол → хаб

### 3.1 Ендпоінт (один для обох плечей)

`POST /api/v1/sync/push` — `torgashka-api/src/router_v1.rs:178`.

* Тіло — **масив агрегатів** (`Vec<PushEnvelope>`), максимум **50** на запит
  (`PUSH_BATCH_MAX`, `sync.rs:712`).
* Відповідь — per-item статуси (`created` | `already_exists` | `error`) **плюс
  `error_class`** (§5) і той самий `X-Sync-Batch-Id` у заголовку відповіді
  (`sync.rs:810-820`).
* Ідемпотентність — `client_uuid` агрегата + partial UNIQUE на приймачах
  (10 індексів, Alembic `0013_sync_push_idempotency.py`). Повтор = `already_exists`,
  дублікатів не буває.
* Кожен агрегат — **окрема транзакція** (`sync.rs:1034`; сам приймач — `sync_receivers.rs`, по одному `begin()/commit()` на агрегат), «батько + рядки» —
  в одній транзакції всередині агрегата (`sync_receivers.rs:272-317, 341-392,
  440-487, 517-561, 676-729`).

**На плечі «каса → вузол»** цим ендпоінтом користується каса (її SQLite-outbox,
`torgashka-infrastructure/src/offline/sync_push.rs`), тобто для вузла він є
**приймачем**. **На плечі «вузол → хаб»** той самий контракт застосовує хаб, а
клієнтом виступає форвардер вузла (§3.2).

**Типи агрегатів (push-kinds), які приймаються** (`sync.rs`, `receiver_table`;
13 таблиць-приймачів, 17 аліасів):

| kind | таблиця-приймач |
|---|---|
| `receipt`, `return_receipt` | `receipts` |
| `purchase_order`, `purchase` | `purchase_orders` |
| `inventory` | `inventories` |
| `transfer`, `transfer_out`, `transfer_in` | `transfers` |
| `write_off` | `write_offs` |
| `invoice` | `invoices` |
| `cash_operation` | `cash_operations` |
| `return_invoice` | `return_invoices` |
| `debtor_payment` | `debtor_payments` |
| `supplier_ledger` | `supplier_ledger` |
| `debtor` (E1) | `debtors` |
| `work_session` (E1) | `work_sessions` |
| `prro_shift` (E1) | `prro_shifts` |

### 3.2 Форвардер вузол → хаб

`torgashka-api/src/hub_forwarder.rs` (фонова tokio-задача на вузлі):

* бере агрегати з черги **`hub_outbox`** і надсилає їх на хаб тим самим
  `POST /api/v1/sync/push`;
* цикл: `DEFAULT_INTERVAL_SECS = 30` с, мінімум `MIN_INTERVAL_SECS = 5` с,
  до `BATCHES_PER_CYCLE = 10` пакетів за цикл (`hub_forwarder.rs:55, 56, 59`);
* retry/backoff — та сама політика, що в черзі каси (`attempts` +
  `next_attempt_at`, стеля 1 год; `MAX_ATTEMPTS`, див. Alembic `0021`);
* штамп батча вузла (`batch_id`) передається на хаб **як є** — на хабі
  `sync_log.batch_id` дорівнює батчу вузла (критерій E3,
  `tests/hub_forwarder_e2e.rs`).

**Черга `hub_outbox`** (Alembic `0021_hub_forwarding.py`):

| Колонка | Зміст |
|---|---|
| `envelope jsonb` | **той самий** конверт, що вузол прийняв від каси (не перезібраний — щоб дані на хабі не розійшлися з локальними) |
| `status` | `pending` \| `done` \| `failed` |
| `attempts`, `next_attempt_at` | backoff/ліміт спроб |
| `batch_id` | штамп батча вузла |
| `forwarded_at`, `forward_status`, `error` | результат спроби |
| `UNIQUE (store_id, client_uuid, entity)` | повторний push того самого агрегата не плодить дублікатів у черзі |

**Стан форвардингу** дублюється в журналі прийому: `sync_log.hub_forwarded_at`
(NULL = ще не поїхало), `sync_log.hub_forward_status` (`accepted` | `failed`),
partial-індекс `ix_sync_log_hub_pending` — «що ще не поїхало».

## 4. Pull: вузол ← хаб

`GET /api/v1/sync/master?entity=<сутність>&since_version=<int>`
(`router_v1.rs:173`).

* Дельти за **`server_version > since_version`** — стабільні, monotonic; версію
  рядку проставляє BEFORE-тригер `bump_sync_version()` у тій самій транзакції,
  що й зміна (Alembic `0011`/`0012`/`0023`/`0024`).
* Пагінація: сторінка `PAGE_SIZE = 500` (`sync.rs:55`), ознака «є ще» +
  `to` (наступний `since_version`) у відповіді — клієнт повторює pull, доки
  `has_more`.
* Видалення передаються як **tombstone** (`is_deleted = true`, `op=delete`) —
  рядок не зникає мовчки.
* Сутності, дозволені для pull (`ALLOWED_ENTITIES`, 9 шт., `sync.rs`):
  `categories`, `products`, `suppliers`, `employees`, `settings`, `barcodes`,
  `product_images`, `write_off_reasons`, `store_product_prices`.
  Інша `entity` → 400 (явна відмова замість порожньої відповіді).
* Сутності без власних версій отримали `server_version` + тригер + рядок у
  `sync_meta` в E5 (Alembic `0023`, `0024`); `stock_norms` видалено з `sync_meta`
  (таблиці не існує).

## 5. Батчі, порядок агрегатів, класи помилок

**Батчі** (Alembic `0020_sync_batches.py` + `sync.rs`):

* `sync_batches(id, store_id, node_id, created_at, items, status)` — рядок
  створюється **до** обробки з песимістичним `failed` і оновлюється за
  фактичним результатом: `accepted` (усі прийняті) | `partial` (частина) |
  `failed` (жодного). «Пакет у процесі» більше не змішується з «загублено».
* `sync_log.batch_id` + `sync_log.error_class` — у кожного агрегата батча.

**Класи помилок** (`sync.rs:719-726`; серверний мапінг SQLSTATE →
`db_error::db_error_class`, `sync.rs:1739-1740`):

| `error_class` | Сенс | Дія клієнта |
|---|---|---|
| `RETRYABLE_FK` | батько ще не прийнятий (SQLSTATE 23503) | **`defer`** — агрегат лишається в черзі, повтор із backoff |
| `VALIDATION` | невалідні дані / чужа major-версія схеми | термінально: агрегат вимагає втручання |
| `CONFLICT` | конфлікт спільної сутності | окрема гілка (див. §6) |

Клієнт каси реалізує саме це: `RETRYABLE_FK` → `defer_or_fail(...)`
(`offline/sync_push.rs:490, 672-679`), 5xx/429 → backoff на весь пакет
(`:625-627`). Наслідок: «дитина приїхала раніше батька» більше **не** стає
вічним `failed` (доказ: `tests/sync_retryable_fk_e2e.rs`), а coalesce «батько
відсутній» вирішується етапом E1 — нові kinds `debtor`/`work_session`/
`prro_shift` (`tests/sync_missing_parents_e2e.rs`).

## 6. Спільні довідники: proposal-протокол (хаб — авторитет)

**Канал:** `POST /api/v1/sync/catalog-proposal` (`router_v1.rs:186-188`);
приймає батч пропозицій (до `PUSH_BATCH_MAX` = 50); відповідь містить
лічильники `accepted` / `conflicts` / `rejected` і per-item рішення
(`torgashka-api/src/catalog_proposal.rs:190-260`).

**Алгоритм (як реалізовано):**

1. Вузол пише локально (offline-first не ламається).
2. Надсилає **пропозицію** `{entity, row_id, op: upsert|delete, payload, client_uuid}`.
   `payload` — конверт **тієї самої форми**, що віддає pull-дельта (щоб вузол не
   мав другого мапінгу).
3. Пропозиція **спочатку лягає в журнал** (`catalog_change_requests`, статус
   `pending`) — жодна правка вузла не зникає.
4. Хаб арбітрує: присвоює **єдиний** `server_version`; для `op=delete` ставить
   tombstone; повертає вузлу `status` + присвоєну версію.
5. Інші вузли отримують результат звичайним pull-ом (§4).
6. `client_uuid` пропозиції UNIQUE: повтор мережевого запиту повертає **раніше
   рішення**, а не створює другу правку.

**Арбітровані сутності — 4** (`ARBITRATED_ENTITIES`,
`catalog_proposal.rs:110-111`): `products`, `suppliers`, `store_product_prices`,
`users`.
* `store_product_prices` — рішення Творця **Б1** (2026-09-12): ціна — атрибут
  **мережі** (єдина канонічна ціна), шлях як у `products.price`.
* `users` — рішення Творця **Б2** (2026-09-16, варіант A): касир створюється
  **локально** на вузлі (offline-first), канонічним стає після прийняття
  пропозиції хабом; стан видно по маркеру `users.sync_state`
  (`local` | `pending_hub` | `confirmed`, Alembic `0024`).

**Свідомо НЕ арбітруються** (не вигадувати процедур — розширення = рядок у
`ARBITRATED_ENTITIES` + `apply_*`): `barcodes`, `product_images`,
`write_off_reasons`, `system_settings` — вони **придатні для pull** (§4), але
власних пропозицій не приймають. `print_templates` — **⏳ відкрите питання**
(§11.3).

## 7. Конфлікти

* Конфлікт = **дві пропозиції на один рядок**. Обидві лишаються в журналі зі
  статусом `conflict` (`catalog_proposal.rs:372-396`) — конфлікт **видимий**, а
  не «злитий» мовчки (last-write-wins за локальним часом вузла ADR прямо
  забороняє).
* Черга для оператора: `GET /api/v1/admin/sync/conflicts`
  (`router_v1.rs:803-806`), доступ `admin|owner|store_manager` (`require_admin`).
  Відповідь **згрупована** за `(entity, row_id)` — щоб оператор бачив усі
  сторони конфлікту разом.
* Відкриті конфлікти видні також у `GET /api/v1/sync/status` →
  `conflicts.open`.

## 8. Стан синку: `GET /api/v1/sync/status`

`router_v1.rs:189`, реалізація `torgashka-api/src/sync_status.rs`.

## 9. Сумісність версій схеми (`X-Schema-Major`, E9)

Проблема: `schema_revision` — **локальна** таблиця кожної БД (DDL мережею не
їде), тому несумісна міграція хаба нікого не зупиняла. Рішення Творця
(2026-09-16, варіант A; блокер Б5 — закрито): major-версія схеми зберігається в
`schema_revision` (`major`, `minor`; Alembic `0025_schema_revision_major.py`), а
хаб **відхиляє push** від вузла з іншою major.

| Елемент | Реалізація |
|---|---|
| Константи | `SCHEMA_MAJOR = 1`, `SCHEMA_MAJOR_HEADER = "X-Schema-Major"`, `UNVERSIONED_MAJOR = 1` — `torgashka-infrastructure/src/sync_schema.rs:32, 41, 51` |
| Заголовок | вузол/каса оголошує свою major у кожному push; хаб **віддає** свій у відповіді (`sync.rs:164-192, 965`) |
| Перевірка | активна **лише на хабі** (`guard_active = !is_node`, `sync.rs:879`; перевірка — `sync.rs:887`): саме хаб приймає дані чужих схем. На вузлі push каси не перевіряється — у каси власної PG-схеми немає, а відмова зламала б локальний прийом чеків |
| Невідповідність | **409** + `error_class = VALIDATION`; **жодного агрегата** не прийнято, `sync_log` чистий, але в `sync_batches` лишається `failed`-рядок — оператор бачить, що вузол стукав і отримав відмову (`sync.rs:887-908`) |
| Вузли до E9 | без заголовка → приписується `UNVERSIONED_MAJOR = 1` (протокол до E9 = major 1). Хаб на major 1: жодного регресу; хаб із піднятою major: **явна** відмова з обома версіями замість тихого псування (`sync_schema.rs:42-50`) |
| Сміттєвий заголовок | не число/нуль → 400 (не «приписати мовчки») |
| Видимість | `schema_major` у `/api/v1/sync/status` — вузол бачить розбіжність заздалегідь, локальним GET |

**Порядок викатки при несумісній зміні схеми:** спершу оновити **вузли**
(вони перестають слати чужу major), і лише потім підняти `SCHEMA_MAJOR` хаба
разом із несумісною міграцією. Зворотний порядок = усі старі вузли отримають
409.

## 10. Хаб недоступний (офлайн-режим вузла)

**Що відбувається (перевірено тестами, не «на словах»):**

| Крок | Факт | Доказ |
|---|---|---|
| Каса пише на вузол | 200, чек прийнято **локально** | `tests/hub_outage_e2e.rs` |
| Вузол не може дістати хаб | агрегат лягає в `hub_outbox` зі `status='pending'` (нічого не губиться, **жодного мовчазного `failed`**) | `hub_outage_e2e.rs:120-128` (черга виросла до 2) |
| Стан журналу | `sync_log.hub_forwarded_at IS NULL` | там же |
| Readiness | `GET /api/v1/setup/status` **НЕ 503** — вузол не read-only | `hub_outage_e2e.rs:96-103` (критерій E4) |
| Хаб піднявся | агрегати доїжджають, `hub_forwarded_at IS NOT NULL` | `hub_outage_e2e.rs:13-21` |
| 4 точки одночасно офлайн | кожна пише локально, після підйому — консистентно, **дублікатів 0**, закупівлі без дублікатів | `tests/sync_4stores_outage_e2e.rs:463-497` |

**Чого НЕ відбувається:** вузол не блокує запис, не віддає 503 через
недоступність хаба і не потребує жодних DR-операцій (promote/repoint більше не
існують). Єдина деградація — черга і лаг (`/api/v1/sync/status`).

Окремо: якщо **каса** не може записати у свій локальний PG, вона не має
вдавати успіх — виправлено в E1.5 (`503` замість `202`,
`tests/receipt_silent_failure_e2e.rs`). Це про локальний збій, не про хаб.

## 11. ⏳ ОЧІКУЄ РІШЕННЯ ТВОРЦЯ (не вигадувати процедур)

### 11.1 ⏳ Б7 — бекап/копія хаба: **НЕ ВИЗНАЧЕНО**

> **Не плутати зі знімком для провіжну вузла (§15).** Знімок БД хаба
> (`pg_dump -Fc`, кнопка «Створити знімок для вузла» / `POST /api/v1/admin/hub-snapshot`)
> — це **реалізований інструмент приєднання нового вузла**: разова копія ВСІЄЇ БД
> хаба в каталозі знімків, яку вузол забирає сам через `GET /api/v1/sync/snapshot`
> (деталі — §15). Він **не** є політикою бекапу: розкладу немає, знімки не
> видаляються й не ротуються, цілісність за розписанням не перевіряється,
> переведення вузлів на інший хаб він не вирішує. Усе нижче лишається ⏳.

**Статус: рішення відсутнє (блокер Б7 плану, §6). Процедури бекапу та копії
(репліки) хаба в ADR-0008 і в цьому документі НЕМАЄ — свідомо.**

Що відомо фактично:

* хаб — звичайна read-write PostgreSQL, тож технічно бекап не відрізняється від
  бекапу будь-якої БД проєкту (наявні загальні матеріали:
  [docs/infrastructure/backup-restore.md](../infrastructure/backup-restore.md) —
  вони описують БД застосунку, **не** процедуру мережі «хаб + вузли»);
* у протоколі синку (ADR-0008 §7) **немає** механізму «перенести роль хаба»:
  роль визначається налаштуванням `sync.hub_url` у БД кожного інстанса, а
  вузли про зміну хаба ніхто не повідомляє (repoint-primary видалено в E7);
* отже питання «як підняти копію хаба і як на неї перевести вузли» **потребує
  рішення Творця** — вигадувати кроки тут заборонено (це ops-процедура з
  ризиком втрати даних мережі).

**Мінімум, який треба вирішити:** (а) як часто й чим знімається бекап хаба;
(б) чи потрібна гаряча копія хаба і в якій формі; (в) як вузли переводяться на
інший хаб (новий `sync.hub_url` + перевірка відсутності дублікатів — механізм
ідемпотентності для цього вже є: `client_uuid` UNIQUE); (г) хто і як перевіряє
цілісність після відновлення.

### 11.2 ⏳ Б6 — ретеншн журналів синку

**Не реалізовано** (видимо в API, жодного «німого TODO»):
`GET /api/v1/sync/status` → `retention: { configured: false, blocker: "..." }`
(`sync_status.rs` — константа `RETENTION_POLICY = None` + `RETENTION_BLOCKER`).
Питання: термін зберігання `sync_log` / `hub_outbox` / вирішених
`catalog_change_requests` + партиціювання. Поки політики немає — **нічого не
видаляється** (свідомо: краще диск, ніж втрачені дані).

### 11.3 ⏳ C4 — `print_templates`

Не синхронізується **свідомо** (Alembic `0023`: ні `server_version`, ні тригера,
ні entity). Причина: несумісність поточної схеми (`UNIQUE (type) WHERE
is_default` = один default на тип **глобально**) з per-store дефолтами точки.
Потрібне рішення: каталог хаба чи локальний оверрайд точки.

### 11.4 Інші відкриті питання (з ADR §10 / плану §6)

| # | Питання | Наслідок |
|---|---|---|
| Б3 | чи потрібні вузлу **чужі** операційні дані (взаємні борги/переміщення між точками) | варіант «так» = новий потік hub → node для операційних даних → **правка ADR-0008** |
| Б4 | мережевий аудит на хабі (`audit_log` ↑) чи локальний | змінює рядок матриці `audit_log` |
| Б8 (E10) | фіскальний аудит мережі: лише push `prro_shifts` чи нічний звіт хаба | E10 не стартує |

**Правило роботи з цими пунктами:** рішення ухвалює Творець; до рішення
жодних «тимчасових» процедур у проді.

## 12. Діагностика: що вважати нормою

| Перевірка | Норма | Що означає відхилення |
|---|---|---|
| `GET /api/v1/sync/status` → `role` | на хабі `hub`, у магазині `node` | `node` без `hub_url` не буває; `role=hub` у магазині = не налаштовано `sync.hub_url` |
| `queue.pending` | 0 (короткочасно >0 — норма під час роботи) | сталe зростання = хаб недоступний/форвардер не працює |
| `queue.failed` | 0 | вичерпано спроби: дивитись `hub_outbox.error` + `sync_log.error_class` |
| `lag_seconds` | малий (одиниці-десятки секунд) | велике значення = найстаріший агрегат не доїхав |
| `conflicts.open` | 0 | є спільні сутності з двома правками → черга `GET /api/v1/admin/sync/conflicts` |
| `schema_major` (вузол vs хаб) | рівні | розбіжність = майбутні 409; див. §9 (порядок викатки) |
| `versions` по сутностях | зростають/стабільні | застрягла версія = немає змін або pull не робиться |
| `retention.configured` | `false` (поки Б6) | — |

> оператор виконує **саме onboarding** — він **канонічний для оператора**.
> **§15.0** лишається докладним технічним довідником (порядок пошуку конфіга з
> посиланнями на код, права, діагностика, пастки). Інструкції **не суперечать** одна
> одній — звірено 13.09.2026: порядок шляхів конфіга (`env` → `%APPDATA%\Torgashka\`
> поряд із `pgdata` → CWD → repo), права `0600` на обидва файли, `.gitignore:149-150`,
> `ssl = off`, версії PG (§0.1).

> 🛑 Увесь текст §15 (скоуп, передумови, кроки 15.1–15.5) описує ІСТОРИЧНУ модель «хаб — окремий HTTP-сервіс». Робоча процедура для топології ZBOX — §15.0 і [onboarding-windows-device.md](./onboarding-windows-device.md); на ZBOX HTTP-фасаду немає (8000/80/443 закриті, перевірено 13.09.2026).

**Скоуп:** додати в мережу нову точку (вузол) на основі БД хаба. Дві гілки —
**мережева (LAN)** і **офлайн (файл)**; результат однаковий: на вузлі розгорнута
БД хаба, вузол налаштований на свій хаб.

**Передумови:** хаб працює; є доступ owner/admin (кнопка створення знімка — це
`require_admin`-операція, §15.1); є **адреса хаба** (напр. `http://192.168.0.10:8000`)
і **токен вузла** (див. §15.5 — як саме він видається, ⏳ не визначено).

> ⚠️ **Передумови вище стосуються ІСТОРИЧНИХ кроків 15.1–15.5** (модель «хаб —
> HTTP-сервіс»). Для підтвердженої топології ZBOX передумови — у **§15.0**, і
> жодної адреси хаба/токена там не потрібно.

### 15.0 РОБОЧА процедура — новий пристрій за моделлю «прямий доступ до БД ZBOX»

**Модель** (рішення Творця **13.09.2026**, §0.1;
[ADR-0009](../adr/ADR-0009-direct-db-sync-model.md)): пристрій підключається
**напряму** до БД ZBOX `10.179.55.210:5432` для синхронізації даних і має
**локальну копію БД**, з якою працює.

**Що потрібно мати, крім застосунку:** **два файли** — `db_sources.toml` і
`.dbkey` (поряд). **Ні** адреси хаба, **ні** токена вузла, **ні** знімка БД,
**ні** майстра `/node-join` ця процедура не потребує.

#### (a) Інсталяція застосунку

1. Взяти Windows-інсталятор із GitHub Release (збірка/реліз —
   [windows-build-plan.md](../windows-build-plan.md); автоапдейт — `latest.json`).
2. Встановити, один раз запустити й закрити — потрібно лише для створення
   каталогів (`%APPDATA%\Torgashka\`, `…\pgdata`).

#### (b) Покласти `db_sources.toml` + `.dbkey` у СТАБІЛЬНИЙ каталог

Основний варіант (обидва файли — в ОДНОМУ каталозі):

```
%APPDATA%\Torgashka\db_sources.toml
%APPDATA%\Torgashka\.dbkey
```

* **Чому саме цей каталог.** Порядок пошуку конфіга (перший знайдений виграє) —
  з коду `crates/torgashka-infrastructure/src/db_sources.rs:31-45`:
  1. env `TORGASHKA_DB_SOURCES` (абсолютний шлях до файла);
  2. **стабільний каталог поряд із `pgdata`** = `%APPDATA%\Torgashka\`
     (Linux: `$XDG_DATA_HOME/Torgashka/` або `~/.local/share/Torgashka/`);
  3. `./db_sources.toml` (CWD) — сумісність зі старими розкладками;
  4. `<repo>/frontend/src-tauri/db_sources.toml` (dev-збірка).
* **Кирилиця в імені користувача Windows:** якщо `%APPDATA%`/`%LOCALAPPDATA%`/temp
  містять не-ASCII, застосунок переходить на ASCII-фолбек
  `C:\ProgramData\Torgashka\pgdata` — і тоді конфіг із ключем кладемо поряд:
  `C:\ProgramData\Torgashka\db_sources.toml` + `.dbkey`.
* **Альтернатива через env** (для розробника/автоматизації, не для звичайного
  оператора): `TORGASHKA_DB_SOURCES=<абс. шлях до toml>` +
  `TORGASHKA_DBKEY=<ключ base64/hex>`; env має пріоритет над файлами.
* **Коли чинний CWD-варіант (кандидат 3):** якщо застосунок запускається з теки,
  де файл лежить. **Факт на цій робочій машині (13.09.2026):** процес `torgashka`
  має CWD = корінь репо, і `db_sources.toml`+`.dbkey` лежать **саме там**, а в
  `~/.local/share/Torgashka/` — лише `torgashka.log`. Для **нових** пристроїв
  використовувати **стабільний** каталог: CWD на проді нестабільний (autostart і
  `restart_app` запускають exe з іншої робочої теки).
* **Запис** (активація джерела, CRUD) завжди йде в **перший** кандидат списку.

#### (c) Права, власник, передача файлів

* `.dbkey` — права **0600** (`rw-------`), власник — користувач, під яким працює
  застосунок. На живій машині саме так (перевірено 13.09.2026: `db_sources.toml`
  і `.dbkey` — `-rw-------`, власник `anastasia`).
* `db_sources.toml` — також 0600: усередині `password_encrypted` (AES-256-GCM).
* `.dbkey` **НЕ МОЖНА**: комітити в git, пересилати месенджерами/поштою, класти в
  спільні теки. Передача на новий пристрій — лише захищеним каналом або фізичним
  носієм.
* Без `.dbkey` пароль **нечитабельний**: застосунок повідомить «файл ключа … не
  читається …; задайте env `TORGASHKA_DBKEY` або створіть `.dbkey` (права 0600)».

#### (d) Що застосунок робить при старті

1. Знаходить `db_sources.toml` за списком (b) і читає `active = "main"`.
2. Бере джерело `main`: `host = "10.179.55.210"`, `port = 5432`,
   `database = "pos_system"`, `user = "postgres"`, `password_encrypted`
   — і розшифровує пароль ключем (`TORGASHKA_DBKEY` → інакше `.dbkey`).
3. Підключається **напряму** до БД ZBOX (саме цей канал везе синхронізацію даних
   за моделлю; жодного HTTP-хаба в шляху немає).
4. Піднімає **локальну копію БД** — вбудований PostgreSQL: `data_dir` =
   `%APPDATA%\Torgashka\pgdata` (Linux `~/.local/share/Torgashka/pgdata`), порт
   `EMBEDDED_PG_PORT = 5433`; listen-адреси задає env
   `TORGASHKA_PG_LISTEN_ADDRESSES` — штатно `-h 127.0.0.1` (лише loopback),
   інакше `-c listen_addresses='<val>'` (`*` або список IP → копія стає
   доступною з мережі)
   (`crates/torgashka-infrastructure/src/embedded_pg.rs:34, 420, 721, 1029-1041`).

> ⚠️ **Що спостережено НАСПРАВДІ (13.09.2026, ця робоча машина) — не приховувати.**
> У логах застосунку при активному зовнішньому джерелі стоїть «
> `DATABASE_URL` ззовні … embedded PG не потрібен», тобто **авто-підйом вбудованої
> копії не виконується**. Локальна копія працює **окремим** процесом:
> `data_dir = /home/anastasia/torgashka_pg_primary`, порт **5544**,
> `listen_addresses=127.0.0.1,192.168.0.160` — тобто **два** слухачі:
> `127.0.0.1:5544` **і** `192.168.0.160:5544` (`ss -tlnp | grep 5544`, обидва —
> pid postgres). ⚠️ `postmaster.pid` віддає **лише ПЕРШУ** адресу зі списку — саме
> тому тут раніше стояло «тільки `127.0.0.1`». **Не** використовувати
> `postmaster.pid` як джерело істини для listen-адрес: перевіряти `ss -tlnp` або
> cmdline процесу (`tr '\0' ' ' < /proc/<pid>/cmdline`). Процес запущений **не**
> застосунком (батько — `systemd --user`). Застосунок тримав **2** з'єднання до
> ZBOX `:5432` (`torgashka` pid 3817757, fd=41 і fd=46) і **жодного** до локальної
> копії `:5544`; решта 3 з 5 ESTAB на `:5432` — окремі сесії `psql` (інші pid).
> **⏳ Відкрите питання до Творця (не вигадувати):** хто і коли піднімає локальну
> копію на пристрої, і чи має застосунок працювати з нею як з робочою БД (а ZBOX —
> як із джерелом синхронізації). До рішення — фіксуємо як є.

> ⏳ **Звірено з [onboarding-windows-device.md](./onboarding-windows-device.md) п.4**
> (там: «на першому старті створить власний локальний кластер у
> `%APPDATA%\Torgashka\pgdata` … підтягне дані в локальну копію»): **що саме піднімає
> і використовує локальну копію — не встановлено; спостережене на dev-машині п.4
> не підтверджує** (авто-підйом копії пропущено, копія — окремий процес, 0 з'єднань
> застосунку до неї). Рішення — за Творцем; текст onboarding п.4 не витирається.

#### (f) Обмеження й пастки (реально наявні)

1. **Потрібен мережевий доступ до `10.179.55.210:5432`** (ZeroTier-оверлей).
   Швидка перевірка (Linux): `timeout 4 bash -c "cat < /dev/null > /dev/tcp/10.179.55.210/5432"`
   → 13.09.2026: **відкрито**; `8000`/`80`/`443` → закрито.
2. **Порядок запуску:** спершу доступна мережа до ZBOX, потім старт застосунку.
   ⏳ Чи повторює застосунок спробу підключення, якщо ZBOX недоступний у момент
   старту, — не встановлено.
3. **`.dbkey` обов'язковий** — без нього `password_encrypted` не розшифрувати (c).
4. **Права на керування джерелами:** CRUD і `/activate` — `require_admin`
   (`owner|admin|store_manager`); **провіжн** джерела
   (`POST /api/v1/admin/db-sources/provision`) — `require_owner`
   (`crates/torgashka-api/src/admin_db_sources.rs:1209-1214`). Окремої «процедури
   активації» не вигадуємо — межа прав саме така.
5. **Пастка порту 5433:** вбудована копія вважає, що якщо `127.0.0.1:5433` уже
   щось слухає, то «embedded PG вже слухає — старт пропущено»
   (`embedded_pg.rs:378-381, 651`). На цій **dev-машині** `5433` займає системний
   PostgreSQL 16 (`/etc/postgresql/16/main/postgresql.conf:64` → `port = 5433`) —
   тобто **чужий** кластер на 5433 буде сприйнятий як «наша копія». На робочих
   Windows-пристроях системного PG бути не повинно; якщо 5433 зайнято — копія не
   підніметься.
6. **Шифрування каналу** — §0.2 (`ssl = off`; у межах ZeroTier прийнятно, поза
   ZeroTier — ні; ⏳ рішення за Творцем).
7. **Чого НЕ потрібно** (щоб не шукати зайвого): адреса хаба `:8000`, токен
   вузла, знімок БД, майстер `/node-join` — це кроки 15.1–15.5, для топології
   ZBOX вони **неактуальні** (нижче).
8. **Локальна копія доступна з LAN** (`listen_addresses=127.0.0.1,192.168.0.160`,
   порт 5544): це (а) додаткова поверхня на пристрої і (б) саме той шлях, яким
   **можливо** мають ходити інші пристрої замість прямого доступу до ZBOX —
   ⏳ питання до Творця: звужувати listen-адреси копії до `127.0.0.1` чи ні?
   Рішення не ухвалено.
9. **Версії PG різні (ZBOX `14.24` ↔ копія `17`)** — фізична реплікація між
   major-версіями неможлива (§0.1); `pg_basebackup`/`primary_conninfo`/слоти **не
   застосовні**, синк — на рівні застосунку. На локальному кластері лишилися
   **рудименти** реплікації (`-c wal_level=replica -c max_wal_senders=10
   -c max_replication_slots=10`, слот `standby_075454c3`,
   `max_slot_wal_keep_size='10GB'`) — ⏳ демонтувати чи лишити (§15.6-D).

> 🔴 **НЕАКТУАЛЬНО для підтвердженої топології (перевірено на живій системі 13.09.2026).**
> Кроки **15.1–15.4** описують модель «хаб — окремий HTTP-сервіс на `:8000`»
> (ADR-0008). У підтвердженій топології **на ZBOX HTTP-фасаду немає**: порт `8000`
> (а також `80`, `443`) — ЗАКРИТИЙ, відкритий лише `5432`. Тому з інструкції
> нижче **фізично не працює**:
> * «адреса хаба» виду `http://<ip>:8000` — недосяжна;
> * «токен вузла» (роль `device`) — не потрібен, бо немає сервісу, до якого його
>   пред'являти;
> * `GET /api/v1/sync/snapshot` по мережі — недосяжний (на ZBOX такого сервісу немає);
> * майстер **`/node-join`** — не має куди підключатися.
>
> **Що робити замість:** [onboarding-windows-device.md](./onboarding-windows-device.md)
> (покроково для оператора) + **§15.0** (докладний технічний довідник). Кроки 15.1–15.5 **збережено як історичні** —
> вони валідні для випадку, коли хаб справді піднято окремим HTTP-сервісом
> (повний перелік розбіжностей — §15.6).

### 15.1 Крок 1 — на хабі: створити знімок

> 🔴 **Неактуально для топології ZBOX** (історичний крок HTTP-моделі; чинний лише для «хаб — окремий HTTP-сервіс»). Заміна — **§15.0**.


1. Хаб → **Налаштування → Джерела даних** → секція «Резервне копіювання (дамп активної БД)».
2. Кнопка **«Створити знімок для вузла»** → `POST /api/v1/admin/hub-snapshot`.
3. UI показує реальний результат: ім'я файла `<БД>_YYYYMMDD_HHMMSS.dump`, розмір,
   sha256 (можна скопіювати) і шлях. Файл лягає в **каталог знімків**
   (`TORGASHKA_HUB_SNAPSHOT_DIR`, типово `artifacts/hub_snapshot`).

Факти й обмеження (перевірено e2e `hub_snapshot_create_e2e`, див. §15.4):

* формат — `pg_dump --format=custom` (`-Fc`) `--no-owner --no-privileges`;
  вузол читає його `pg_restore` (plain SQL `-Fp` для цієї мети не годиться);
* знімок — **уся** БД хаба (дані всіх точок мережі), а не дані однієї точки;
* **вузол бере найновіший за mtime `*.dump`** із каталогу; перезапуск хаба не
  потрібен — каталог читається на кожен запит (кешу немає);
* два знімки в одну секунду → другий отримує суфікс `-NN`; наявний файл **не**
  перезаписується;
* невдалий/порожній файл видаляється, відповідь — `400` з хвостом stderr;
* **ротації немає**: старі знімки ніхто не видаляє (це інструмент приєднання, не
  бекап-політика — §11.1). Якщо у каталозі лежить новіший файл — вузол забере саме його;
* права: створення — `require_admin` (`owner|admin|store_manager`, як «Експортувати
  дамп»); забирання знімка — `device|admin|owner` (`store_manager`/`cashier` → `403`).

### 15.2 Крок 2 — на вузлі: майстер «Приєднати до мережі»

> 🔴 **Неактуально для топології ZBOX** (історичний крок HTTP-моделі; чинний лише для «хаб — окремий HTTP-сервіс»). Заміна — **§15.0**.


Вхід: екран входу (або setup) → **«Це не головний комп'ютер — приєднати до мережі»**
→ маршрут **`/node-join`**.

1. Заповніть **адресу хаба** (нормалізується до `http(s)://host:port`) і **токен вузла**.
2. Джерело знімка:
   * **мережева гілка (LAN)** — нічого додатково не вибирайте: вузол сам завантажить
     найновіший знімок із хаба (`GET /api/v1/sync/snapshot`); отриманий sha256
     звіряється із заголовком `X-Snapshot-Sha256` (розбіжність = помилка завантаження);
   * **офлайн-гілка** — позначте режим локального файла → «Обрати файл…» → вкажіть
     `.dump`, заздалегідь скопійований з хаба (флешка / спільна тека).
3. Запустіть провіжн. Майстер показує 4 кроки: перевірка хаба → завантаження
   (або читання) файла → відновлення БД → активація вузла. Помилки показуються
   реальним текстом (у т.ч. хвіст stderr `pg_restore`), класи:
   `BadUrl`, `HubUnreachable`, `DownloadFailed`, `RestoreFailed`, `DbUnavailable`.
4. Після `ok = true` застосунок перезапускається сам.

**Офлайн-гілка не потребує ні доступності хаба, ні оновлення його версії** —
потрібен лише файл знімка. Адреса й токен хаба все одно записуються в БД вузла:
вони потрібні для подальшого синку (§2, §3), коли хаб стане доступним.

### 15.3 Крок 3 — вхід на вузлі

> 🔴 **Неактуально для топології ZBOX** (історичний крок HTTP-моделі; чинний лише для «хаб — окремий HTTP-сервіс»). Заміна — **§15.0**.


У БД вузла лежить відновлена база хаба, тому **вхід виконується вашим наявним PIN**
(`POST /api/v1/auth/login-pin`) — окрема реєстрація/налаштування користувачів не
потрібні. Перевірка після входу: `GET /api/v1/sync/status` → `role = node`,
`hub_url` = введена адреса хаба.

### 15.4 Що саме перевірено тестом

> 🔴 **Неактуально для топології ZBOX** (історичний крок HTTP-моделі; чинний лише для «хаб — окремий HTTP-сервіс»). Заміна — **§15.0**.


`frontend/src-tauri/crates/torgashka-api/tests/hub_snapshot_create_e2e.rs` (штатний
HTTP-шлях, не «прямий виклик функції»):

1. `POST /api/v1/admin/hub-snapshot` роллю admin → `200`, `ok=true`, файл існує за
   `path`, `bytes > 0`, sha256 у відповіді = sha256 ЗАПИСАНОГО файла;
2. того ж процесу, **без перезапуску**, `GET /api/v1/sync/snapshot` роллю `device`
   → `200`, `x-snapshot-filename`/`x-snapshot-sha256`/`content-length` = щойно
   створеному файлу (інваріант «створив → вузол одразу забрав»);
3. `pg_restore -l` бачить TOC, `pg_restore` у чисту БД дає **ті самі `count(*)`**,
   що джерело;
4. негативи: без токена → `401`; `device` на POST → `403`; недосяжне активне
   джерело → `400`, каталог знімків не змінюється (жодного обрізаного файла);
5. два POST в одну секунду → два різні файли (`-01`), обидва валідні.

Офлайн-гілка (крок 2, «локальний файл») покрита окремим e2e
`contract2_restore_e2e`: `source=file`, `pg_restore` з файла, запис `sync.hub_url`
і `sync.hub_token` у БД вузла, `role=node` у `GET /api/v1/sync/status`.

### 15.5 ⏳ Відкрите питання — як оператор отримує **токен вузла**

> 🔴 **НЕАКТУАЛЬНО для моделі прямого доступу до БД (13.09.2026).** Токен вузла
> потрібен лише HTTP-шляху (знімок через `GET /api/v1/sync/snapshot`). За
> моделлю «прямий доступ до БД ZBOX» жодних токенів не потрібно — потрібні
> `db_sources.toml` + `.dbkey` (§15.0). Текст нижче збережено як історичний.

Знімок забирається з роллю `device`. Фактично сьогодні:

* реєстр вузлів (`POST /api/v1/admin/network-nodes`) генерує `join_code`, але
  **ендпоінта обміну join-коду на токен немає** (демонтовано в E7) — тож «код
  активації» **не** є робочим способом отримати токен вузла;
* робочий механізм видачі токена з роллю `device` — активація пристрою точки:
  `POST /api/v1/admin/stores/:store_id/activation-code` → `POST /api/v1/devices/activate`
  (публічний), який повертає токен пристрою.

Як саме оператор має видавати токен **вузлу** (окремий owner-ендпоінт? обмін
join-коду? токен із реєстру вузлів?) — **⏳ рішення Творця, процедуру не
вигадувати** (той самий стиль, що §11).
