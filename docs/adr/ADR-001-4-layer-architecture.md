# ADR-001: 4-шарова архітектура (Clean Architecture)

| Метадані | Значення |
|----------|----------|
| **Статус** | ✅ Прийнято |
| **Дата** | 2026-07-20 |
| **Автор** | System Architect Agent (AEGIS v3) |
| **Версія** | 1.0.0 |

---

## Контекст

Поточна архітектура kasa/ має спрощену 3-шарову структуру:
- `api/v1/` — роутери (Presentation)
- `services/` — бізнес-логіка (змішана Application + Domain)
- `models/` — SQLAlchemy моделі (Infrastructure)

**Проблеми поточної архітектури:**
1. **Порушення Dependency Rule:** `services/` напряму імпортують `models/` (SQLAlchemy), що унеможливлює тестування без БД
2. **Відсутність Domain шару:** Бізнес-логіка змішана з інфраструктурним кодом
3. **Жорстка залежність від SQLAlchemy:** При зміні ORM доведеться переписувати всі сервіси
4. **Важке тестування:** Неможливо замокати репозиторій, потрібна реальна БД

## Рішення

Впровадити 4-шарову архітектуру Clean Architecture:

```
┌─────────────────────────────────────────────────────────────────────┐
│  1. Presentation Layer (api/v1/)                                    │
│     Відповідальність: HTTP, валідація запитів, Swagger             │
│     Залежить від: Application Layer                                 │
├─────────────────────────────────────────────────────────────────────┤
│  2. Application Layer (application/)                                │
│     Відповідальність: Use Cases, DTO, Mappers, оркестрація         │
│     Залежить від: Domain Layer                                      │
├─────────────────────────────────────────────────────────────────────┤
│  3. Domain Layer (domain/)                                          │
│     Відповідальність: Entities, Value Objects, Events, Interfaces  │
│     Залежить від: Нічого (чистий Python)                            │
├─────────────────────────────────────────────────────────────────────┤
│  4. Infrastructure Layer (infrastructure/)                          │
│     Відповідальність: Репозиторії, ORM, DI, зовнішні API           │
│     Залежить від: Domain Layer                                      │
└─────────────────────────────────────────────────────────────────────┘
```

## Обґрунтування

1. **Dependency Rule:** Залежності напрямлені всередину. Зовнішні шари знають про внутрішні, але не навпаки.
2. **Тестування:** Domain та Application шари можна тестувати без БД, використовуючи моки репозиторіїв.
3. **Гнучкість:** Можна замінити SQLAlchemy на іншу ORM, змінивши тільки Infrastructure шар.
4. **Чистота коду:** Кожен шар має чітку відповідальність, код стає більш читабельним.

## Альтернативи

| Альтернатива | За | Проти |
|-------------|-----|-------|
| **Залишити 3 шари** | Менше коду | Всі проблеми залишаються |
| **CQRS + Event Sourcing** | Максимальна гнучкість | Overkill для POS-системи |
| **MVC (Django-style)** | Простота | Немає чіткого розділення |

## Наслідки

**Позитивні:**
- ✅ Чітке розділення відповідальності
- ✅ Можливість unit-тестування бізнес-логіки
- ✅ Незалежність від фреймворків
- ✅ Легка заміна ORM/БД

**Негативні:**
- ❌ Більше коду (інтерфейси, маппери)
- ❌ Вища крива навчання для нових розробників
- ❌ Потрібен рефакторинг існуючого коду

## Реалізація

1. Створити `app/domain/` з чистими Python entities
2. Створити `app/application/` з Use Cases
3. Перейменувати `app/models/` → `app/infrastructure/persistence/models/`
4. Створити репозиторії в `app/infrastructure/persistence/repositories/`
5. Оновити роутери для роботи через Use Cases
6. Додати DI контейнер
