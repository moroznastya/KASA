# ADR 015: Offline-first архітектура (4 каси + сервер-агрегатор)

## Статус
✅ Прийнято (2026-09-10)

## Контекст

Бізнес-вимога: **4 фізичні каси (магазини) в одній LAN**, кожна каса має
працювати **завжди** — незалежно від стану мережі, сервера чи інтернету.
Поточна архітектура (етап 1–6 мультиточковості, ADR-001…014) — онлайн:
каса читає/пише PostgreSQL напряму через Rust-фасад (`resolve_database_url`:
env → `backend/.env` → embedded PG). При втраті зв'язку з сервером каса
деградує до кешу товарів та черги чеків (`offline/db.rs`, SQLite) — тобто
**offline — виняток, а не основний режим**.

Цей ADR фіксує інверсію: **SQLite на касі стає ОСНОВНИМ робочим сховищем**,
PostgreSQL на сервері — **агрегатором та точкою адміністрування**. Потоки
даних — **однонапрямлені**, що усуває клас конфліктів синхронізації
(CRDT/LWW/merge не потрібні).

### Факти з наявних артефактів

1. **`offline/db.rs` (SQLite, сьогодні):** таблиці `products` (id TEXT PK,
   data JSON, store_id, updated_at), `receipts` (id INTEGER AUTOINCREMENT,
   data JSON, store_id, synced), `settings` (key, value). Міграції —
   ідемпотентні `ensure_column` (PRAGMA table_info → ALTER TABLE ADD COLUMN).
   `PRAGMA user_version` **не використовується**.
2. **Multi-store план (затверджений 2026-08-20):** каталог `products`
   глобальний; кількість/ціна — per store у `stock(store_id, product_id,
   quantity, price)`; `user_stores(user_id, store_id, role, permissions,
   is_default)`; RLS — другий контур (`current_setting('app.store_id')`);
   `store_id` на всіх документах (receipts, invoices, transfers, inventories,
   purchase_orders, return_invoices, debtors, work_sessions…).
3. **Режим агрегатора вже частково існує:** `connect_readonly_pool` для
   довідників (READ), embedded PostgreSQL як fallback.

### Вимоги Творця (підтверджено)

- Топологія: 4 каси + локальний сервер в LAN.
- **Кожна каса має локальну SQLite — виключно для свого магазину**; це
  ОСНОВНЕ робоче сховище (offline-first, каса працює завжди).
- Сервер — загальна PostgreSQL для всіх магазинів: агрегатор + адміністрування.
- Потоки ОДНОНАПРЯМЛЕНІ (без конфліктів):
  * Майстер-дані (товари, ціни, групи, постачальники, працівники,
    налаштування): **сервер → каса** (pull; каса читає локально, не редагує).
  * Транзакції (чеки, повернення, закупки, інвентаризації, переміщення):
    **каса → сервер** (push; сервер лише приймає).
- Сервер = джерело істини для довідників; каса = джерело істини для своїх
  транзакцій.
- Адміністрування просте: завів магазин на сервері → каса сама підтягнула
  довідники.

## Рішення

**Offline-first:** SQLite на касі — основне сховище; PostgreSQL на сервері —
агрегатор. Синхронізація — **однонапрямлений pull/push через версійовані
дельти та ідемпотентні client-UUID транзакції** (детальний дизайн —
`docs/design/sync-schema-design.md`, ЕТАП 1).

### Архітектурні принципи

1. **Каса — самодостатня одиниця.** Всі операції продажу/повернення/закупки/
   інвентаризації/переміщення виконуються виключно проти локальної SQLite.
   Каса не робить жодного синхронного write-запиту до сервера.
2. **Один магазин — одна каса.** `offline.db` прив'язується до `store_id`
   (запис у `settings` + перевірка при старті). Перенос БД на іншу точку —
   заборонений (контроль по `settings.store_id`).
3. **Pull (майстер-дані):** каса періодично (або за подією) запитує дельти
   з версії `since_version` → атомарно застосовує до локальних таблиць →
   зберігає нову версію в `sync_meta`. Локально майстер-дані **тільки
   читаються** (крім налаштувань, що є локальними — окремий простір ключів).
4. **Push (транзакції):** кожна транзакція пишеться в локальну SQLite **в
   одній транзакції з її ефектами** (stock, борг) + у **outbox** з
   `client_uuid` (UUIDv4, генерується на касі). Фоновий синк-процес відправляє
   outbox на сервер; сервер приймає **ідемпотентно** (UNIQUE client_uuid).
5. **Версії замість timestamp-злиття.** Конфліктів немає за конструкцією:
   кожна сутність має одного власника запису. Дельти — суто додатні (сервер
   віддає rows з version > since; каса віддає нові client_uuid).
6. **RLS залишається на сервері** як другий контур для адміністрування та
   зведених звітів. На SQLite RLS технічно неможливий — локальний контур
   каси = шифрування файлу БД (SQLCipher, spike підтвердив) + локальна
   авторизація за PIN. **Це не суперечність, а два різні контури безпеки.**

### Місце в існуючій схемі (узгодження з multi-store планом)

| Сутність multi-store | Роль в offline-first |
|---|---|
| `stores`, `user_stores` | Довідник, pull на касу. Каса знає ТІЛЬКИ свій store_id та своїх працівників |
| `stock(store_id, product_id, quantity, price)` | На сервері — **проєкція** прийнятих транзакцій кас (агрегатор). На касі — локальний `stock` (свій store_id), джерело істини для кількості |
| `products` (глобальний каталог, barcode UNIQUE) | Джерело істини — сервер; каса отримує копію через pull; soft-delete (`is_deleted`) |
| `store_id` на документах | Генерується на касі з `settings.store_id`; сервер валідує через X-Store-Id (існуючий StoreCtx) |
| RLS | Діє на сервері для адмін-доступу; каса проходить як store-суб'єкт зі своїм store_id |
| `resolve_database_url` | **Більше не використовується касою для операційних write.** Залишається для адмін-режиму (зведені звіти власника, керування довідниками) та embedded PG — legacy-режим, деградує до read-only |

### Компоненти

```
┌─────────────┐   pull (дельти, since_version)   ┌──────────────────┐
│ Каса 1..4   │ ───────────────────────────────▶ │ Локальний сервер │
│ SQLite      │ ◀─────────────────────────────── │ PostgreSQL       │
│ (offline.db)│   push (outbox, client_uuid)     │ (агрегатор)      │
└─────────────┘                                  └──────────────────┘
     ▲  локальні операції (завжди)                     ▲
     │  продаж/повернення/закупка/інвентаризація        │ адміністрування, зведені звіти
     └──────────────────────────────────────────────────┘ (веб-UI власника)
```

## Альтернативи, що розглядалися

| Альтернатива | Чому відхилена |
|---|---|
| **(a) Централізована PostgreSQL для кас** (поточний стан: каса пишеться напряму в PG) | При втраті LAN каса не працює взагалі — порушує головну вимогу «каса працює завжди». LAN + локальний сервер = єдина точка відмови для 4 магазинів. Офлайн-режим довелося б будувати паралельно з повним дублюванням логіки — зараз він уже існує (offline/db.rs), але як виняток, з усіма ризиками незафіксованого стану |
|---|---|
| **(b) Реплікація PG (streaming/logical) до SQLite або PG→PG** | 1) SQLite не є реплікаційним target для native PG replication. 2) Двонапрямлена реплікація = конфлікти (два магазини змінюють один рядок), потрібен merge/CRDT — суперечить вимозі «однонапрямленість без конфліктів». 3) PG→PG (серверний вузол у кожному магазині) — надмірність: на касі не потрібен повний SQL-сервер, це збільшує TCO і складність моніторингу. 4) Версії ЛВВ (last-write-wins) дають втрату даних за конструкцією |
|---|---|
| **(c) CRDT / автономний merge** (типу Automerge/Yjs) | Зайва складність для моделі, де конфлікти відсутні за побудовою: майстер-дані мають одного власника (сервер), транзакції — одного власника (каса). CRDT додає векторні годинники, семантику merge і накладні витрати без жодної вимоги, яку вони закривають |
|---|---|
| **(d) Повний офлайн у сенсі «каса ніколи не синхронізується»** | Не відповідає вимозі адміністрування: власник має бачити зведені дані по 4 точках на сервері. Синхронізація потрібна, але вона однонапрямлена та асинхронна |
|---|---|
| **(e) SQLCipher лише для чеків, решта — відкрито** | Шифрування БД — атомарна властивість файлу (вся БД або нічого). Часткове шифрування не дає захисту: метадані (товари, налаштування) теж конфіденційні. Рішення: вся `offline.db` — SQLCipher (ключ у OS keyring) |

## Наслідки

✅ **Переваги:**
- Каса працює **завжди**: продажі не залежать від LAN, сервера, інтернету.
- Конфліктів синхронізації немає **за конструкцією** — не потрібні merge,
  CRDT, ЛВВ, ручні резолюції.
- Сервер простий: агрегатор + адміністрування; навантаження на PG мінімальне
  (прийом дельт + віддача дельт).
- Масштабування: додавання каси = створення магазину на сервері + перший pull;
  без зміни схеми.
- Офлайн-інфраструктура (SQLite, WAL, черга) вже існує — розширюємо, не будуємо з нуля.

⚠️ **Ризики та пом'якшення:**

| Ризик | Вплив | Пом'якшення |
|---|---|---|
| Зміна ціни на сервері під час продажу (каса продала за стару) | Розбіжність виручки | Продаж фіксує `price_snapshot` у items чека (як зараз у multi-store: «історія цін — в items»). Сервер не перераховує ціну ретроспективно |
| Видалення товару на сервері | Каса продає видалений товар | Soft-delete (`is_deleted`) у дельті; каса прибирає товар з продажу при наступному pull. Відкриті чеки не ламаються (items зберігають снапшот назви/ціни) |
| Тривала відсутність зв'язку (тижні) | Розростання outbox | Обмеження: розмір outbox моніториться; чеки зберігаються безстроково (вимога ДПС — 3 роки), інші транзакції теж. Backoff до 1 год + повтор при відновленні зв'язку |
| Фіскалізація ПРРО потребує інтернету (ДПС) | Чек продано, але не зафіскалізовано | ПРРО офлайн-режим ДПС (до 72 год): чек зберігається зі статусом `pending_fiscal`; при відновленні зв'язку фіскалізується ПЕРЕД push. Статусна модель в sync-schema-design |
| SQLCipher ключ втрачено | БД не читається | Ключ в OS keyring (секретна служба); резервна копія ключа у власника — окремий процес (поза цим ADR) |
| Каса почала працювати без первісного pull (порожній каталог) | Неможливо продавати | Онбординг каси: перший pull обов'язковий (екран «Очікування синхронізації»), після успіху — каса розблокована |
| Агрегатор відстає (pull/push затримки) | Зведені звіти не миттєві | SLA: pull-інтервал 30 с у LAN; зведені звіти позначаються часом останньої синхронізації кожної точки (`sync_log`) |
