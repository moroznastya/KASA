## 1. Що таке «мережа магазинів» у Torgashka

Мережа = **один власник (owner) — багато торговельних точок (stores)**.
Масштаб: від 1 каси (single-store) до мережі точок у різних містах. Кожна
точка має свої: залишки (`stock`), ціни (базові в `products` + оверрайди в
`store_product_prices`), касирів/адмінів (прив'язка в `user_stores`), фіскальні
налаштування (`prro_settings`), зміни (`prro_shifts`), касові операції
(`cash_operations`), пристрої (`devices`).

**Ключова модель розмежування:** ролі й права живуть на рівні точки
(`user_stores`), а не в `users`. Один касир може бути перекинутий з точки в
точку одним UPDATE'ом `user_stores`, не торкаючись `users`.

Ролі користувачів (ENUM `user_role`): `admin`, `cashier`, `owner`,
`store_manager`. Ролі на точку (`user_stores.role`): `owner`, `admin`, `cashier`.

## 2. Схема мережевих таблиць (актуальний DDL із schema.sql)

### 2.1 `stores` — точки мережі
```sql
CREATE TABLE public.stores (
    id          uuid DEFAULT uuid_generate_v4() NOT NULL,
    name        varchar(255) NOT NULL,
    address     varchar(500),
    phone       varchar(50),
    legal_name  varchar(255),      -- юр. назва власника точки
    edrpou      varchar(20),       -- ЄДРПОУ
    is_active   boolean DEFAULT true NOT NULL,
    created_at  timestamptz DEFAULT now() NOT NULL,
    updated_at  timestamptz DEFAULT now() NOT NULL,
    CONSTRAINT stores_pkey PRIMARY KEY (id)
);
```

### 2.2 `user_stores` — центральна таблиця мультиточковості
```sql
CREATE TABLE public.user_stores (
    user_id     uuid NOT NULL,     -- FK → users (CASCADE)
    store_id    uuid NOT NULL,     -- FK → stores (CASCADE)
    role        varchar(16) DEFAULT 'cashier' NOT NULL,  -- owner|admin|cashier
    permissions jsonb DEFAULT '{}' NOT NULL,             -- per-store права
    is_default  boolean DEFAULT false NOT NULL,          -- точка за замовчуванням
    created_at  timestamptz DEFAULT now() NOT NULL,
    CONSTRAINT user_stores_pkey PRIMARY KEY (user_id, store_id)
);
CREATE INDEX ix_user_stores_store ON user_stores(store_id);
CREATE INDEX ix_user_stores_role  ON user_stores(role);
```

### 2.3 `devices` — фізичні каси мережі (життєвий цикл)
```sql
DO $$ BEGIN
    IF NOT EXISTS (SELECT 1 FROM pg_type WHERE typname = 'device_status') THEN
        CREATE TYPE public.device_status AS ENUM ('pending','active','blocked','deleted');
    END IF;
END $$;

CREATE TABLE public.devices (
    id                uuid DEFAULT uuid_generate_v4() NOT NULL,
    store_id          uuid NOT NULL,                    -- FK → stores (CASCADE)
    name              varchar(255) NOT NULL,
    device_token_hash varchar(255) NOT NULL,            -- SHA-256 токена пристрою
    source            varchar(50),                      -- напр. 'legacy_migration'
    status            device_status DEFAULT 'pending' NOT NULL,
    app_version       varchar(50),
    last_seen_at      timestamptz,
    activated_at      timestamptz,
    created_at        timestamptz DEFAULT now() NOT NULL,
    updated_at        timestamptz DEFAULT now() NOT NULL,
    CONSTRAINT devices_pkey PRIMARY KEY (id),
    CONSTRAINT devices_store_id_fkey FOREIGN KEY (store_id)
        REFERENCES stores(id) ON DELETE CASCADE
);
CREATE INDEX ix_devices_store_id ON devices(store_id);
-- не більше одного legacy-пристрою на точку (ідемпотентність /admin/migrate/legacy)
CREATE UNIQUE INDEX ux_devices_legacy_migration_store
    ON devices(store_id) WHERE (source = 'legacy_migration');
```

### 2.4 `store_activation_codes` — коди активації точок
```sql
-- код 8 символів; varchar(9) — резерв під префікс; один рядок на магазин,
-- повторна генерація оновлює код (regenerated_at)
CREATE TABLE public.store_activation_codes (
    store_id        uuid NOT NULL,
    code            varchar(9) NOT NULL,     -- UNIQUE
    created_by      uuid,                    -- FK → users (SET NULL)
    created_at      timestamptz DEFAULT now(),
    regenerated_at  timestamptz,
    CONSTRAINT store_activation_codes_pkey PRIMARY KEY (store_id),
    CONSTRAINT store_activation_codes_code_key UNIQUE (code)
);
```

### 2.5 `store_sync_state` — стан синхронізації точки
```sql
CREATE TABLE public.store_sync_state (
    store_id        uuid NOT NULL,           -- PK, FK → stores (CASCADE)
    device_id       uuid,                    -- FK → devices (SET NULL)
    last_synced_at  timestamptz,
    last_local_seq  bigint DEFAULT 0 NOT NULL,  -- останній локальний seq точки
    status          varchar(20) DEFAULT 'unknown' NOT NULL
);
```

### 2.6 `store_product_prices` — ціна товару по конкретній точці
```sql
CREATE TABLE public.store_product_prices (
    id          uuid DEFAULT uuid_generate_v4() NOT NULL,
    store_id    uuid NOT NULL,               -- FK → stores (CASCADE)
    product_id  uuid NOT NULL,               -- FK → products (CASCADE)
    price       numeric(10,2) NOT NULL,
    created_at  timestamptz DEFAULT now(),
    updated_at  timestamptz DEFAULT now(),
    CONSTRAINT store_product_prices_pkey PRIMARY KEY (id),
    CONSTRAINT store_product_prices_store_id_product_id_key UNIQUE (store_id, product_id)
);
```

### 2.7 `audit_log` — аудит адмін-дій мережі
```sql
CREATE TABLE public.audit_log (
    id            uuid DEFAULT uuid_generate_v4() NOT NULL,
    actor_user_id uuid,                        -- FK → users (SET NULL: слід зберігається)
    action        varchar(100) NOT NULL,       -- напр. store.create, device.block
    entity_type   varchar(50),                 -- store|user|device|...
    entity_id     uuid,
    store_id      uuid,                        -- FK → stores (SET NULL)
    payload       jsonb,                       -- контекст дії
    created_at    timestamptz DEFAULT now()
);
CREATE INDEX ix_audit_log_store_id_created_at ON audit_log(store_id, created_at);
```

### 2.8 `owners_db` — database-per-owner (мета-рівень, Частина 2)
```sql
CREATE TABLE public.owners_db (
    owner_id    uuid NOT NULL,                 -- PK, FK → users (CASCADE)
    db_name     text NOT NULL UNIQUE,          -- напр. torgashka_owner_<uuid>
    created_at  timestamptz DEFAULT now()
);
```

### 2.9 store_id на бізнес-таблицях
`store_id uuid` + `FK → stores(id) ON DELETE CASCADE` присутній на: `barcodes`,
`categories`, `debtors`, `debtor_payments`, `inventories`, `inventory_items`,
`invoice_items`, `invoices`, `product_images`, `purchase_order_items`,
`purchase_orders`, `receipt_items`, `receipts`, `return_invoice_items`,
`return_invoices`, `supplier_ledger`, `system_settings`, `transfer_items`,
`transfers`, `work_sessions`, `write_off_items`, `write_offs`,
`prro_settings`, `prro_shifts`, `prro_queue_items`, `print_templates`.
`stock` — композитний PK `(store_id, product_id)`. `products` — **без**
store_id (глобальний каталог мережі). `cash_operations`, `devices` — store_id NOT NULL.

## 3. Ролі і доступ: приклад (власник + 3 точки + 4 працівники)

```sql
INSERT INTO stores (id,name,address) VALUES
 ('s1','Мій магазин','вул. Хрещатик, 1'),
 ('s2','Філія на Лівому березі','вул. Броварська, 15'),
 ('s3','Склад-магазин','вул. Промислова, 3');

INSERT INTO user_stores (user_id,store_id,role,permissions,is_default) VALUES
 ('u1','s1','owner','{"*":true}', TRUE),   -- Ірина — всі 3 точки
 ('u1','s2','owner','{"*":true}', FALSE),
 ('u1','s3','owner','{"*":true}', FALSE),
 ('u2','s2','admin','{"*":true}', TRUE),   -- Максим — адмін s2
 ('u3','s2','cashier','{"pos.sell":true}', TRUE),   -- Олег — касир s2
 ('u4','s3','cashier','{"pos.sell":true}', TRUE);   -- Наталя — касир s3
```

Наслідки: «скільки точок у власника» = count(user_stores) by owner = 3;
касир з 1 записом не бачить switcher; `is_default` визначає точку входу;
права на точку — у `permissions` (jsonb), не в `users`.

## 4. Ізоляція даних точок (RLS + StorePool)

**Політика на кожній бізнес-таблиці** (`<table>_store_isolation`):
```sql
ALTER TABLE <table> ENABLE ROW LEVEL SECURITY;
CREATE POLICY <table>_store_isolation ON <table>
  USING (store_id = NULLIF(current_setting('app.store_id', true),'')::uuid
      OR store_id IN (SELECT store_id FROM user_stores
                      WHERE user_id = NULLIF(current_setting('app.user_id', true),'')::uuid))
  WITH CHECK (…той самий вираз…);
```
`user_stores` — політика `user_stores_self` (user_id = current user).

**Механізм проставляння контексту (Rust, `store_ctx.rs`):**
- Middleware фасаду (`store_context.rs:65 store_middleware`) валідує JWT +
  `X-Store-Id`; кладе `StoreCtx{user_id, store_id, role}` у `tokio::task_local`.
- Відповіді без контексту: бізнес-запит без `X-Store-Id` → **400**; точка поза
  `user_stores` користувача → **403**.
- `StorePool` (обгортка PgPool): транзакції/запити виконуються з
  `set_config('app.store_id'|'app.user_id', …, is_local)`, після запиту —
  reset (NULLIF('')-семантика, щоб контекст не протікав у пул).
- Owner-політика «бачити всі свої точки» забезпечує міжточкові звіти та
  пошук наявності без зміни SQL.

**Стан:** RLS увімкнено на таблицях; реальне форсування (`FORCE ROW LEVEL
SECURITY` + робота під роллю `torgashka_app` замість власника таблиць) —
етап 7 плану (`sources/database-architecture-implementation-plan.md §3`).

## 5. Активація каси в мережі (життєвий цикл пристрою)

1. **Створення точки** (owner): `POST /api/v1/admin/stores` →
   `repositories/stores.rs::create`: INSERT stores + прив'язка творця як owner
   (`user_stores`) + **авто-seed**: системні налаштування точки
   (`system_settings`) і шаблони друку (`print_templates`) по замовчуванню.
2. **Код активації**: `POST /api/v1/admin/stores/:store_id/activation-code`
   (owner) → генерує/оновлює 8-символьний код у `store_activation_codes`
   (UNIQUE, `regenerated_at`). Повторна генерація інвалідизує старий код.
3. **Активація каси** (публічний, без JWT): `POST /api/v1/devices/activate`
   з `{code, device_fingerprint}`:
   - rate-limit за IP (негайно 429 при перевищенні);
   - код → JOIN stores → назва точки;
   - генерується одноразовий `device_token`; у БД — лише SHA-256-хеш;
   - INSERT `devices(store_id, name, device_token_hash, status='active')`;
   - відповідь: `{device_token, device_id, store_id, store_name}`.
4. **Подальша робота каси**: токен пристрою зберігається локально
   (`services/tauri/offline.ts` + Rust), використовується для автентифікації
   при синхронізації; `store_id` каси = її точка.
5. **Управління** (owner): `GET /api/v1/admin/devices` (список зі статусами),
   `POST /:device_id/block`, `POST /:device_id/unblock`,
   `DELETE /api/v1/admin/devices/:device_id`. Статуси: pending → active →
   blocked/deleted.

## 7. Касові операції мережі (інкасація/внесення)

Таблиця `cash_operations`:
- `operation_type` CHECK IN (`deposit` — внесення, `collection` — інкасація);
- `cash_type` CHECK IN (`cash`, `card`);
- `amount > 0`, `store_id` NOT NULL (операція завжди належить точці), user_id.

Звіти: `/api/v1/admin/reports/cash-operations` (по всіх точках мережі);
UI: `network/NetworkFinancesPage.tsx`. Дизайн і правила балансу —
`sources/multi-store-and-cash-operations.md §6`.

## 8. Синхронізація мережі (offline-first)

**Pull (сервер → каса):** `GET /api/v1/sync/master?entity=…&since_version=N`
- сутності: `categories, products, stock_norms, suppliers, employees, settings`;
- серверний `server_version` проставляється BEFORE-тригером на момент зміни;
  дельта = рядки з `server_version > N`, відповідь: `{changes[], to, has_more}`;
- каса пише в нормалізовані SQLite-таблиці (0003) з soft-delete.

**Push (каса → сервер):** `POST /api/v1/sync/push`
- агрегати з локального `outbox`: чек/повернення/замовлення/інвентаризація/
  переміщення/списання/борг/каса;
- ідемпотентність: `client_uuid` (UUIDv4) → сервер: created | already_exists;
- атомарність: транзакція + ефекти (stock, ledger, cash) в одній транзакції;
- retry/backoff, логування в `sync_log`, стан точки на сервері —
  `store_sync_state(last_local_seq, last_synced_at, status)`.

**Локальні залишки:** SQLite `stock` (0005) — каса знає свій залишок офлайн;
списання на сервері — атомарне `UPDATE … WHERE quantity >= qty`.

**Фіскальний офлайн:** ПРРО-черга (`prro_queue_items`/SQLite) до 168 год,
після відновлення — push + фіскалізація.

## 11. Розгортання мережі: топології та провізія

- **A. Desktop single** (одна каса / малий магазин): embedded PostgreSQL у
  data dir застосунку (`embedded_pg.rs`, bootstrap при першому запуску);
  БД = одна точка.
- **B. Серверний (мережа точок)**: центральний PostgreSQL (Docker
  `docker-compose.yml`, PostgreSQL 16); owner провізіює БД через
  `/admin/db-sources/provision` (роль `torgashka_app`, schema.sql, статуси
  джерела); кожна каса — клієнт мережі з локальним SQLite.
- **C. SaaS / кілька власників**: database-per-owner через `owners_db`;
  план — «пул пулів» з LRU-кешем і маршрутизацією за `users.owner_id`
  (етап 9, `sources/database-architecture-implementation-plan.md §5`).
