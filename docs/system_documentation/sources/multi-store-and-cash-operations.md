# Дизайн: мультиточковість + готівкові операції (інкасація/внесення) + онбординг

> Статус: ПРОПОЗИЦІЯ (аналіз, без реалізації)
> Дата: 2026-08-20 (оновлено за зауваженнями Творця)
> Стек: Rust-фасад (torgashka-*) + React + PostgreSQL

---

## 0. КЛЮЧОВІ РІШЕННЯ (за зауваженнями Творця)

1. **Зміни каси (відкриття/закриття) — НЕ реалізуємо** (на цьому етапі).
2. **Інкасація та внесення коштів — поза вікном каси (POS)**, окремий адмін-модуль
   «Каса». Доступні **тільки адміністраторам** (owner/admin), ніколи касиру.
3. **Наявність товару в інших точках** — для касира це **просто пункт у sidebar**
   (read-only пошук), не блок у POS/картці товару.
4. Для власника — попередньо описаний UX (switcher точок, звіти) залишається.
5. Додано **онбординг при встановленні**: перший запуск → майстер створення
   власника → точки → каси. Вся подальша робота прив'язана до власника і точок.

## 1. ВСТАНОВЛЕННЯ ПРОГРАМИ (ДЕТАЛЬНО)

### 1.1 Варіанти встановлення

| Варіант | Для кого | Що ставиться | База даних |
|---|---|---|---|
| **A. Desktop-пакет (Tauri)** | магазин з одним ПК на касі | `.deb`/`AppImage` — один інсталятор | **вбудована PostgreSQL** (локальна, автозапуск) або зовнішня |
| **B. Серверний** | мережа точок (2+ ПК) | backend (Rust-фасад) + frontend на сервері, desktop/браузер на касі | PostgreSQL на сервері (docker або systemd) |
| **C. Dev-режим** | розробник | `cargo run` + `npm run dev` | локальний PostgreSQL |

Нижче детально описані A і B — вони покривають реальні сценарії користувача.

### 1.2 Варіант A — Desktop-пакет (одна каса / малий магазин)

**Інсталятор** (`.deb` для Linux, далі — `.msi`/`.dmg`):
- Ставить: бінарник Tauri (React UI + Rust-фасад), **вбудований PostgreSQL 16**
  (окремий data-dir у `~/.local/share/torgashka/`), системний юніт для автозапуску БД.
- Створює конфіг `~/.config/torgashka/config.toml`:
  ```toml
  [database]
  url = "postgres://torgashka:<генерований_пароль>@127.0.0.1:5432/torgashka"
  embedded = true          # вбудована БД
  [server]
  host = "127.0.0.1"
  port = 8000
  [app]
  data_dir = "~/.local/share/torgashka"
  ```
  Пароль БД генерується при встановленні і зберігається тільки в конфігу
  (права `0600`). Користувач **не бачить і не вводить** жодних параметрів БД.

**Що відбувається при першому запуску (автоматично, ~10–20 сек):**
1. Перевірка/підйом вбудованої PostgreSQL (`pg_ctl start`), якщо не запущена.
2. Створення БД `torgashka` і користувача (якщо немає).
3. **Авто-міграції**: застосування схемних міграцій (аналог `alembic upgrade head`,
   але в Rust-фасаді — `sqlx::migrate!` або власний раннер). Ідемпотентно:
   повторний запуск не ламає схему.
4. `GET /api/v1/setup/status` → `not_initialized` → UI показує майстер онбордингу.

**Екран «Підключення...» (сплеш):**
```
┌────────────────────────────────────────────┐
│  🏬 Torgashka POS                          │
│                                            │
│  Підготовка бази даних...                  │
│  ████████████░░░░░░░░  60%                 │
│  [Застосування міграцій...]                │
└────────────────────────────────────────────┘
```
Якщо щось пішло не так (БД не стартує, порт зайнятий) — екран помилки з
діагностикою: «Не вдалося запустити базу даних. Перевірте, що порт 5432 вільний.
[Спробувати ще] [Показати журнал]».

### 1.3 Варіант B — Серверний (мережа точок)

**На сервері (Ubuntu/Debian):**
```bash
# 1. PostgreSQL 16
sudo apt install postgresql-16
sudo systemctl enable --now postgresql

# 2. Створення БД і користувача (одноразово)
sudo -u postgres psql -c "CREATE USER torgashka WITH PASSWORD '<пароль>';"
sudo -u postgres psql -c "CREATE DATABASE torgashka OWNER torgashka;"

# 3. Встановлення застосунку
sudo dpkg -i torgashka-server.deb        # ставить Rust-фасад + frontend (static)
sudo systemctl enable --now torgashka    # юніт: слухає :8000

# 4. Міграції (авто при старті сервісу або вручну)
sudo torgashka migrate up
```
- Сервер слухає `http://<ip>:8000`. React-збірка віддається як static.
- **На касах** — desktop-клієнт у режимі «підключення до сервера»:
  конфіг клієнта містить `server_url = "http://<ip>:8000"` (вводиться один раз
  при першому запуску клієнта, зберігається локально).
- PostgreSQL **не вбудовується** в клієнт — він працює тільки як віддалений
  клієнт до сервера. Офлайн-режим працює локально (SQLite), синхронізується
  при відновленні зв'язку.

**Екран налаштування клієнта (перший запуск):**
```
┌────────────────────────────────────────────┐
│  Підключення до сервера                    │
│  Адреса сервера: [ http://192.168.1.10:8000 ]│
│  [Перевірити з'єднання]                    │
│  ✅ З'єднання успішне                      │
│  [Далі →]                                  │
└────────────────────────────────────────────┘
```
Після успішної перевірки — той самий майстер онбордингу, що й у варіанті A
(якщо сервер ще не ініціалізований) або звичайний екран входу.

### 1.4 Спільний сценарій після встановлення

```
┌─ Перший запуск ─────────────────────────────────────────────┐
│                                                             │
│  ┌─ підготовка БД (варіант A: вбудована; B: зовнішня) ─┐    │
│  │ міграції → setup/status → not_initialized           │    │
│  └──────────────────────────────────────────────────────┘   │
│                          ↓                                  │
│  ┌─ МАЙСТЕР ОНБОРДИНГУ (4 кроки) ───────────────────────┐   │
│  │ 1. Власник → 2. Точка → 3. Каса → 4. Готово          │   │
│  └──────────────────────────────────────────────────────┘   │
│                          ↓                                  │
│              Головний екран (власник, активна точка)        │
└─────────────────────────────────────────────────────────────┘
```

### 1.5 Повторні запуски

- **Desktop:** запуск → сплеш (перевірка БД, ~2–5 сек) → `setup/status`
  = `initialized` → екран входу. Без майстра.
- **Сервер:** сервіс уже працює; клієнти просто відкривають екран входу.
- **Оновлення версії:** інсталятор замінює бінарники; при старті авто-міграції
  застосовують нові схеми (якщо є). Дані не чіпаються.

### 1.6 Що робити, якщо система вже встановлена (міграція старої версії)

Оновлення існуючої інсталяції з даними:
1. При першому старті нової версії — міграції додають `stores`/`user_stores`/
   `cash_registers`/`cash_operations` + `store_id`.
2. **Seed «Основна точка»**: назва з `system_settings.shop_name` (якщо є),
   інакше «Основна точка». Усі наявні дані → ця точка.
3. Наявні користувачі: `admin` → `owner` (зв'язок з основною точкою),
   `cashier` → `cashier` (зв'язок з основною точкою).
4. `setup/status` = `initialized` → **майстер НЕ показується** — одразу екран
   входу. Користувач входить під своїм логіном як раніше, але тепер все
   в межах «Основної точки».

## 2. ОНБОРДИНГ: ВІД ПЕРШОГО ЗАПУСКУ ДО ПЕРШОГО ПРОДАЖУ

### 2.1 Логіка

**Принцип:** система не може працювати без власника і хоча б однієї точки.
Поки система не ініціалізована — жоден інший екран недоступний.

```
GET /api/v1/setup/status
  ├─ "not_initialized" → майстер онбордингу (нижче)
  └─ "initialized"     → звичайний екран входу
```

### 2.2 Майстер першого налаштування (4 кроки)

**Крок 1 — Власник:**
```
┌────────────────────────────────────────────┐
│  Ласкаво просимо! Створіть обліковий запис │
│  власника мережі.                          │
│  Ім'я:        [________________]            │
│  Логін:       [________________]            │
│  Пароль:      [________________]            │
│  PIN (опц.):  [______]                      │
│                [Далі →]                     │
└────────────────────────────────────────────┘
```
Створюється користувач з роллю **`owner`** (нова роль; має всі права на всі
точки, які будуть створені). Це і є **прив'язка системи до власника**.

**Крок 2 — Перша точка (магазин):**
```
┌────────────────────────────────────────────┐
│  Створіть вашу першу торговельну точку     │
│  Назва:       [Мій магазин        ]         │
│  Адреса:      [вул. Центральна, 1 ]         │
│  Телефон:     [________________]            │
│                [← Назад]   [Далі →]         │
└────────────────────────────────────────────┘
```
Створюється запис у `stores` + зв'язок `user_stores(owner, store)`.
Це перша точка — вона стає **точкою за замовчуванням** для власника.

**Крок 3 — Перша каса:**
```
┌────────────────────────────────────────────┐
│  Налаштуйте касу                           │
│  Точка:       [Мій магазин       ▾]         │
│  Назва каси:  [Каса №1            ]         │
│  Стартовий залишок готівки: [ 0.00 ] грн    │
│                [← Назад]   [Завершити]      │
└────────────────────────────────────────────┘
```
Створюється `cash_registers` (прив'язана до точки) з початковим балансом.
Якщо кас кілька (наприклад, 2 каси в магазині) — власник може додати ще
пізніше з адмін-модуля «Каса».

**Крок 4 — Готово:**
```
┌────────────────────────────────────────────┐
│  ✅ Систему налаштовано!                    │
│  Власник: Ірина · Точка: Мій магазин       │
│  Каса: Каса №1                             │
│  [Перейти до системи]                      │
└────────────────────────────────────────────┘
```
Автоматичний вхід як власник → головний екран зі switcher'ом точок.

### 2.3 Що далі робить власник (після онбордингу)

- **Створює касирів** («Користувачі» → «+ Касир»): ім'я, логін, пароль,
  PIN, **прив'язка до точки**, роль (`admin` точки або `cashier`), пермішени.
- **Створює ще точки** («Налаштування» → «Точки» або новий пункт «Точки»).
- **Створює каси** в точках (адмін-модуль «Каса» → «+ Каса»).
- Далі: товари, постачальники, ПРРО — як зараз, але в межах активної точки.

## 3. РОЗМЕЖУВАННЯ ДАНИХ ЗА ТОРГОВЕЛЬНИМИ ТОЧКАМИ

### 3.1 Варіанти архітектури

| Варіант | Опис | Плюси | Мінуси | Висновок |
|---|---|---|---|---|
| **A. Окрема БД на точку** | кожна точка = окрема PostgreSQL БД | повна ізоляція, простий бек-ап | неможливі міжточкові запити, міграції × N БД, складна оркестрація | ❌ відхилено |
| **B. Одна БД, окрема schema** | PostgreSQL schemas + `search_path` | ізоляція на рівні СКБД | міжточкові запити вимагають перемикання схем, міграції × N схем | ⚠️ надмірно |
| **C. Одна БД, колонка `store_id`** | мульти-тенант + RLS | міжточкові запити тривіальні, одна схема, стандарт | вимагає дисципліни фільтрації | ✅ **рекомендовано** |

**Рекомендація: C** — одна БД, `store_id` FK на всіх бізнес-таблицях +
**Row-Level Security** як захисний другий контур.

### 3.2 Схема

**Нові таблиці:**
```
stores
  id UUID PK, name, address, phone, is_active BOOL,
  created_at, updated_at

user_stores                      -- користувач ↔ точка (роль/права на рівні точки)
  user_id FK, store_id FK, role ENUM('owner','admin','cashier'),
  permissions JSONB, is_default BOOL, PK(user_id, store_id)
```

**Ролі користувачів (розширення поточної моделі):**
| Роль | Хто | Права |
|---|---|---|
| `owner` | власник мережі (створюється в онбордингу) | усі точки, керування точками/касами/користувачами, інкасації, звіти |
| `admin` | адміністратор точки (призначений власником) | своя точка: товари/чеки/звіти, внесення/інкасація, каси |
| `cashier` | касир точки | своя точка: POS-продажі, перегляд наявності в інших точках |

**Каталог `products` — ГЛОБАЛЬНИЙ** (один товар на всі магазини власника,
`barcode` UNIQUE — без дублікатів ШК). `products.stock`/`products.price`
виносяться в таблицю `stock` (кількість і ціна per store).

```
stock                            -- залишки per store
  store_id UUID FK, product_id UUID FK,
  quantity NUMERIC(10,3) NOT NULL DEFAULT 0,
  price NUMERIC(10,2) NOT NULL DEFAULT 0,
  updated_at TIMESTAMPTZ,
  PRIMARY KEY (store_id, product_id)
```
Рядок на кожен магазин, де є товар. «Окрема кількість для магазину» = рядок
зі своїм `store_id`, НЕ окрема таблиця (антипатерн: DDL у runtime, неможливі
зведені запити, міграції × N).

**Додати `store_id` (NOT NULL після backfill) до:**
`barcodes`, `categories`, `receipts`, `receipt_items`, `invoices`,
`invoice_items`, `transfers`, `transfer_items`, `write_offs`, `write_off_items`,
`return_invoices`, `return_invoice_items`, `purchase_orders`,
`purchase_order_items`, `inventories`, `inventory_items`, `debtors`,
`debtor_payments`, `supplier_ledger`, `work_sessions`, `print_templates`,
`system_settings`, `cash_registers`, `cash_operations`.

**Спільні довідники:** `suppliers` — спільні (зв'язок через `supplier_products`
та накладні, там `store_id`). `categories` — на точку.

**Індекси:** композитні `(store_id, created_at)`, `(store_id, barcode)`,
`stock(store_id, product_id)` PK (пошук за ШК у межах точки — критичний шлях POS).

### 3.3 Стратегія міграції (для існуючих інсталяцій)

1. `stores` + `user_stores` + `cash_registers` + `cash_operations`.
2. Seed: точка «Основна точка» (назва з `system_settings.shop_name`, якщо є).
3. Всі існуючі користувачі з роллю `admin` → стають `owner` і отримують
   зв'язок `user_stores` з основною точкою; `cashier` — теж зв'язок.
4. `store_id` як NULLABLE → backfill → `ALTER ... SET NOT NULL`.
5. RLS: `ENABLE ROW LEVEL SECURITY` + політика `store_id = current_setting('app.store_id')`.
6. Перенести `role`/`permissions` з `users` у `user_stores` (зворотна сумісність
   на перехідний період).

### 3.4 РЕАЛІЗАЦІЯ В БД: ОДИН ВЛАСНИК — КІЛЬКА ТОЧОК (ДЕТАЛЬНО)

#### 3.4.1 DDL ключових таблиць

```sql
-- ============================================================
-- Точки (магазини) мережі
-- ============================================================
CREATE TABLE stores (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name        VARCHAR(255) NOT NULL,
    address     VARCHAR(500),
    phone       VARCHAR(50),
    is_active   BOOLEAN NOT NULL DEFAULT TRUE,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ============================================================
-- Зв'язок користувач ↔ точка: РОЛЬ І ПРАВА НА РІВНІ ТОЧКИ.
-- Це центральна таблиця мультиточковості: один owner може мати
-- N записів (по одному на кожну свою точку); касир — зазвичай 1.
-- ============================================================
CREATE TABLE user_stores (
    user_id     UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    store_id    UUID NOT NULL REFERENCES stores(id) ON DELETE CASCADE,
    role        VARCHAR(16) NOT NULL CHECK (role IN ('owner','admin','cashier')),
    permissions JSONB NOT NULL DEFAULT '{}'::jsonb,   -- per-store пермішени
    is_default  BOOLEAN NOT NULL DEFAULT FALSE,        -- точка за замовчуванням
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, store_id)
);

CREATE INDEX idx_user_stores_store ON user_stores(store_id);
CREATE INDEX idx_user_stores_role  ON user_stores(role);

-- ============================================================
-- Кожна бізнес-таблиця отримує store_id (на прикладі products):
-- ============================================================
ALTER TABLE products ADD COLUMN store_id UUID;
ALTER TABLE products ADD CONSTRAINT fk_products_store
    FOREIGN KEY (store_id) REFERENCES stores(id) ON DELETE CASCADE;
-- після backfill:
ALTER TABLE products ALTER COLUMN store_id SET NOT NULL;
CREATE INDEX idx_products_store_barcode ON products(store_id, barcode);
CREATE INDEX idx_products_store_search  ON products(store_id, lower(name) text_pattern_ops);
```

#### 3.4.2 Приклад даних: власник Ірина, 3 точки, 4 працівники

```sql
-- stores: три точки мережі
INSERT INTO stores (id, name, address) VALUES
  ('s1', 'Мій магазин',           'вул. Хрещатик, 1'),
  ('s2', 'Філія на Лівому березі','вул. Броварська, 15'),
  ('s3', 'Склад-магазин',         'вул. Промислова, 3');

-- users: власник + 1 адмін + 2 касири
INSERT INTO users (id, name, login, password_hash, pin) VALUES
  ('u1', 'Ірина', 'iryna',   '***', '1234'),
  ('u2', 'Максим', 'max',    '***', '2222'),
  ('u3', 'Олег',   'oleh',   '***', '3333'),
  ('u4', 'Наталя', 'nata',   '***', '4444');

-- user_stores: Головне — РОЛЬ І ПРАВА ЖИВУТЬ ТУТ, а не в users.
-- Ірина (owner) — прив'язана до ВСІХ трьох точок.
-- Максим (admin) — адмін однієї точки (s2).
-- Олег (cashier) — касир тільки s2.
-- Наталя (cashier) — касир тільки s3.
INSERT INTO user_stores (user_id, store_id, role, permissions, is_default) VALUES
  ('u1','s1','owner','{"*":true}', TRUE),   -- Ірина: точка за замовчуванням
  ('u1','s2','owner','{"*":true}', FALSE),
  ('u1','s3','owner','{"*":true}', FALSE),
  ('u2','s2','admin','{"*":true}', TRUE),
  ('u3','s2','cashier','{"pos.sell":true,"inventory.view_other_stores":true}', TRUE),
  ('u4','s3','cashier','{"pos.sell":true,"inventory.view_other_stores":true}', TRUE);
```

**Як це читається:**
- «Скільки точок у власника Ірини?» → `SELECT count(*) FROM user_stores WHERE user_id='u1'` → **3**.
- «До яких точок має доступ Олег?» → 1 запис → **тільки s2**.
- «Чи може Олег перемкнути точку?» → 1 запис у `user_stores` → **ні**, UI не показує switcher.
- «Яка точка активна за замовчуванням у Ірини?» → `WHERE user_id='u1' AND is_default` → s1.

**Жодних даних у таблицях `users` про точки немає** — `users` залишається
чистим довідником (логін, пароль, PIN, активність). Уся прив'язка — через
`user_stores`. Це дозволяє одного касира перекинути з точки s2 в s3 одним
UPDATE'ом `user_stores`, не чіпаючи `users`.

#### 3.4.3 RLS: другий контур захисту (обов'язковий)

Навіть якщо програміст забуде `WHERE store_id = ...` у запиті — PostgreSQL
**сам не віддасть рядки чужої точки**. Механізм:

```sql
-- 1) Увімкнути RLS на всіх бізнес-таблицях
ALTER TABLE products      ENABLE ROW LEVEL SECURITY;
ALTER TABLE receipts      ENABLE ROW LEVEL SECURITY;
ALTER TABLE cash_operations ENABLE ROW LEVEL SECURITY;
-- ... і так на кожній таблиці зі store_id

-- 2) Типова політика: рядок видно, якщо його store_id дорівнює
--    значенню, яке backend поклав у сесію запиту.
CREATE POLICY store_isolation ON products
    USING (store_id = current_setting('app.store_id', true)::uuid);

-- 3) Для owner — політика «бачити всі свої точки» (потрібна для
--    міжточкового пошуку наявності). Робиться через JOIN user_stores:
CREATE POLICY owner_sees_all_own_stores ON products
    USING (
        store_id IN (
            SELECT store_id FROM user_stores
            WHERE user_id = current_setting('app.user_id', true)::uuid
              AND role = 'owner'
        )
    );
```

**Як backend проставляє контекст (Rust-фасад, axum):**

```rust
// Middleware StoreContext: після валідації токена і заголовка X-Store-Id
// виконує на кожному запиті:
sqlx::query(
    "SELECT set_config('app.user_id',  $1, true),
            set_config('app.store_id', $2, true)"
)
.bind(user_id).bind(store_id)
.execute(&pool).await?;
```

Третій аргумент `true` = `is_local` → значення живе **тільки в межах поточної
транзакції/запиту** і не протікає в інші з'єднання пулу. Після запиту пул
повертає з'єднання чистим.

**Наслідки:**
- Запит без `X-Store-Id` на бізнес-ендпоінт → 400 (middleware).
- Запит з чужою точкою (не з `user_stores`) → 403 (валідація доступу).
- «Забутий» фільтр у SQL → RLS поверне 0 рядків (тихо, без помилки),
  а не чужі дані.
- Інкасація каси точки s2 користувачем, який не має доступу до s2 →
  RLS блокує UPDATE/INSERT у `cash_operations` для чужого `store_id`.

#### 3.4.4 Типові запити в термінах мультиточковості

```sql
-- 1. Список точок користувача при вході (для switcher'а):
SELECT s.id, s.name, s.address, us.role, us.is_default
FROM user_stores us
JOIN stores s ON s.id = us.store_id
WHERE us.user_id = $1 AND s.is_active
ORDER BY us.is_default DESC, s.name;

-- 2. Пошук товару за ШК В МЕЖАХ АКТИВНОЇ ТОЧКИ (критичний шлях POS):
SELECT * FROM products
WHERE store_id = current_setting('app.store_id', true)::uuid
  AND barcode = $1;

-- 3. Міжточкова наявність (sidebar «Наявність в інших точках»):
--    знайти товар по всіх точках, до яких користувач має доступ
SELECT s.name AS store_name, p.title, p.price, p.stock, p.updated_at
FROM products p
JOIN stores s ON s.id = p.store_id
JOIN user_stores us ON us.store_id = p.store_id
WHERE us.user_id = $1
  AND (p.barcode = $2 OR lower(p.title) LIKE '%' || lower($3) || '%')
ORDER BY s.name;

-- 4. Продажі поточного дня по всіх точках власника (звіт):
SELECT s.name, count(r.id) AS receipts, sum(r.total) AS revenue
FROM receipts r
JOIN stores s ON s.id = r.store_id
JOIN user_stores us ON us.store_id = r.store_id
WHERE us.user_id = $1 AND us.role = 'owner'
  AND r.created_at >= date_trunc('day', now())
GROUP BY s.name;

-- 5. Перекинути касира Олега з s2 на s3 (одна операція):
UPDATE user_stores SET store_id = 's3' WHERE user_id = 'u3' AND store_id = 's2';
```

#### 3.4.5 Як «поточна точка» живе між запитами

| Шар | Де зберігається активна точка |
|---|---|
| Frontend | `authStore.activeStoreId` (Zustand) + `localStorage` (переживає перезавантаження) |
| Між frontend і backend | заголовок `X-Store-Id` на кожному запиті (axios-інтерцептор) |
| Backend | middleware валідує і кладе `store_id` у контекст + `current_setting('app.store_id')` |
| БД | RLS-політика читає `current_setting('app.store_id')` — рядки інших точок невидимі |

**У самій БД «активна точка» НЕ зберігається** — це стан сесії користувача,
а не дані. `is_default` у `user_stores` — лише початковий вибір при вході.
Кожен запит несе свою точку явно (`X-Store-Id`), тому перемикання миттєве
і не потребує жодних UPDATE'ів у БД.

#### 3.4.6 Сценарій: власник додає нову точку (крок за кроком)

```
1. POST /api/v1/stores {name, address, phone}
   → INSERT INTO stores ...                  -- 1 рядок у stores

2. Backend автоматично (у тій самій транзакції):
   INSERT INTO user_stores (user_id, store_id, role, permissions)
   VALUES ($owner_id, $new_store_id, 'owner', '{"*":true}');
   → власник одразу має доступ до нової точки

3. POST /api/v1/cash-registers {store_id: $new_store_id, name: "Каса №1"}
   → INSERT INTO cash_registers ...          -- каса в новій точці

4. POST /api/v1/users {name, login, ..., store_id: $new_store_id, role: 'cashier'}
   → INSERT INTO users + INSERT INTO user_stores (cashier, нова точка)

5. Власник перемикає switcher на нову точку → X-Store-Id = $new_store_id
   → всі запити йдуть у межах нової точки; RLS пропускає (owner має зв'язок)
```

Весь процес створення точки = 2–3 INSERT'и, без жодної зміни схеми.
Схема БД **не розмножується** на точки — дані розділяються значенням
`store_id`, а доступ — рядками `user_stores`.

### 3.4.7 Глобальний каталог + stock per store (наслідок рішення)

**Як це працює:**

```sql
-- products: ОДИН запис на товар (молоко 7% — один рядок на всі магазини)
INSERT INTO products (id, title, barcode, ...) VALUES
  ('p1', 'Молоко 7% 900г', '4820000000001', ...);

-- stock: кількість і ЦІНА окремо для кожного магазину
INSERT INTO stock (store_id, product_id, quantity, price) VALUES
  ('s1', 'p1', 18.000, 24.50),   -- Мій магазин:    18 шт, 24.50 грн
  ('s2', 'p1',  6.000, 26.00),   -- Філія:           6 шт, 26.00 грн
  ('s3', 'p1',  0.000, 24.90);   -- Склад-магазин:   0 шт (товар є в каталозі)
```

- Товар, якого немає в магазині → просто немає рядка в `stock` (або quantity=0).
- Продаж у точці s2 змінює ТІЛЬКИ `stock(store_id='s2')` — s1 і s3 не чіпаються.
- Міжточкова наявність = один запит по `stock` з фільтром store_id:
  ```sql
  SELECT s.name, st.quantity, st.price
  FROM stock st JOIN stores s ON s.id = st.store_id
  WHERE st.product_id = $1 AND s.id IN (доступні точки)
  ```
- Зведений залишок по всіх точках власника = `SUM(quantity) GROUP BY product_id`.

**Атомарність складських операцій (без гонок):**

```sql
-- Продаж 1 шт у точці s2: зменшує ТІЛЬКИ s2; 0 рядків → «недостатньо»
UPDATE stock SET quantity = quantity - 1
WHERE store_id = 's2' AND product_id = 'p1' AND quantity >= 1;

-- Надходження 10 шт у s2: створює або збільшує
INSERT INTO stock (store_id, product_id, quantity, price)
VALUES ('s2', 'p1', 10.000, 26.00)
ON CONFLICT (store_id, product_id)
DO UPDATE SET quantity = stock.quantity + EXCLUDED.quantity,
              price = EXCLUDED.price;
```

**Наслідки для решти коду:**
- Усі SELECT залишків: `LEFT JOIN stock` + `COALESCE(quantity, 0)` (товар може
  бути в каталозі, але без рядка в stock точки).
- `products.price`/`products.stock` більше НЕ існують — API повертає ціну/залишок
  через stock активної точки.
- POS: пошук товару за ШК → рядок products (глобально) + рядок stock активної
  точки (ціна/залишок).

## 4. ПЕРЕМИКАННЯ МІЖ ТОЧКАМИ

### 4.1 Backend

- `auth` повертає: список точок користувача + `default_store_id`.
- Middleware `StoreContext`: заголовок **`X-Store-Id`** → валідація доступу
  через `user_stores` → `store_id` у контексті запиту.
- Жоден бізнес-запит не може бути без точки (окрім системних: точки, setup).
- Redis-кеш: ключі з префіксом `store:{store_id}:...`.

### 4.2 Frontend

- **Власник/адмін з кількома точками:** switcher у шапці:
  ```
  [🏬 Мій магазин ▾]  [👤 Ірина]
  ```
  Вибір → зміна `activeStoreId` у Zustand → axios-інтерцептор додає
  `X-Store-Id` → дані сторінки перезавантажуються.
- **Касир:** жорстко прив'язаний до своєї точки через `user_stores` —
  switcher не показується, `X-Store-Id` береться з його зв'язку.
- При вході — автовибір `default_store_id`.

## 6. КАСОВІ ОПЕРАЦІЇ: ІНКАСАЦІЯ ТА ВНЕСЕННЯ (АДМІН-МОДУЛЬ)

### 6.1 Принципи

- **Поза вікном каси (POS):** жодних кнопок інкасації/внесення на POS-екрані.
  Це окремий адмін-модуль «Каса» у sidebar.
- **Тільки адміністратори:** `owner` та `admin` (пермішени `cash.deposit`,
  `cash.collect`). Касир цих операцій **не бачить і не має**.
- **Без змін каси:** немає відкриття/закриття зміни, немає обліку
  «хто на зміні». Каса — це постійний об'єкт з накопичувальним балансом.

### 6.2 Схема

```
cash_registers           — каси (фізичні/логічні грошові ящики)
  id, store_id FK, name, is_active, opening_balance NUMERIC(12,2) DEFAULT 0,
  created_at, updated_at

cash_operations          — рух готівки (внесення/інкасація)
  id, store_id FK, register_id FK, user_id FK,
  operation_type ENUM('deposit','collection'),
  amount NUMERIC(12,2) CHECK (amount > 0),
  balance_after NUMERIC(12,2),        -- баланс каси після операції
  collection_bag_number VARCHAR(20) NULL,  -- номер інкасаторської сумки
  comment TEXT, created_at
```

### 6.3 Логіка балансу (без змін каси)

```
balance(каса) =
    opening_balance
  + Σ (cash_amount − change_amount) з чеків каси       -- готівкові продажі
  + Σ deposit    (внесення)
  − Σ collection (інкасації)
```

- Баланс — **розрахункова величина** (SQL-агрегація по чеках + операціях),
  рахується на льоту, без зберігання суперечливих копій.
- **Внесення (deposit):** поповнення каси (розмінна монета, стартовий капітал).
- **Інкасація (collection):** вилучення виручки. Сума **не може перевищувати
  поточний розрахунковий баланс** (перевірка в транзакції).
- Кожна операція — атомарна транзакція; `balance_after` обчислюється
  сервером (не клієнтом), щоб виключити гонки/підробку.
- *(Опційно, наступний крок)* — «Інвентаризація каси»: адмін фіксує фактичний
  залишок, система показує розбіжність. Поки — поза обсягом.

## 7. UX — ЯК ЦЕ ВИГЛЯДАЄ ЗІ СТОРОНИ КОРИСТУВАЧА

### 7.1 Встановлення та перший запуск (стисло, деталі — розділ 1)

**Нова інсталяція (Desktop A):**
1. Користувач запускає інсталятор, натискає «Далі» × 3, «Встановити».
2. Перший запуск: сплеш «Підготовка бази даних...» (авто-міграції).
3. Майстер (4 кроки): **власник → точка → каса → готово**.
4. Після завершення — одразу в системі як власник, активна точка — перша.

**Нова інсталяція (Сервер B):**
1. На сервері: PostgreSQL + пакет + `systemctl enable --now torgashka`.
2. На касі: desktop-клієнт → ввід адреси сервера → перевірка → майстер/вхід.

**Існуюча інсталяція (міграція):**
1. Оновлення → авто-міграції → «Основна точка» зі всіма даними.
2. Адміни → власники, касири → прив'язані до основної точки.
3. Майстер НЕ показується — одразу вхід.

### 7.2 Роль «Власник» (owner)

- **Вхід** → switcher точок у шапці → перемикання < 1 сек.
- **Створює точки** («Точки» або «Налаштування»): назва, адреса, телефон.
- **Створює каси** («Каса» → «+ Додати касу»): точка, назва, стартовий залишок.
- **Керує користувачами** («Користувачі»): створює адмінів точок і касирів,
  прив'язує до точки, призначає роль і пермішени.
- **Проводить внесення/інкасації** через «Каса» (див. 6.4).
- **Дивиться наявність** в усіх точках через sidebar «Наявність в інших точках».
- **Звіти**: рух готівки за період, інкасації за місяць (по точках).

### 7.3 Роль «Адмін точки» (admin)

- Та сама точка завжди; якщо адмін прив'язаний до кількох — switcher є.
- Має «Каса» в sidebar: **внесення/інкасація по своїй точці**, історія, друк.
- Має «Наявність в інших точках».
- **Не бачить** точки, до яких не прив'язаний.

### 7.4 Роль «Касир» (cashier)

- Вхід (логін/PIN) → одразу POS своєї точки. Switcher точок **відсутній**.
- POS: продажі, повернення, боржники, чеки — як зараз.
- **У sidebar — додаткова опція «Наявність в інших точках»**:
  шукає товар/сканує ШК → бачить, де і скільки є по інших точках (read-only).
- **Не бачить і не має** жодних касових операцій: немає пункту «Каса»,
  немає кнопок внесення/інкасації, API повертає 403.
- Якщо власник зняв пермішен `inventory.view_other_stores` — пункт у sidebar
  зникає.

### 7.5 Обмеження (що бачить користувач)

- **Перемикання точки** — тільки якщо користувач має > 1 зв'язок у `user_stores`.
- **Інкасація > балансу** — заблоковано з підказкою.
- **Офлайн**: касир працює в своїй точці; синхронізація повертає чеки в точку
  продажу (у офлайн-схему додається `store_id`).
- **Доступ**: недоступні пункти меню/кнопки не показуються.

### 7.6 Сценарії для приймальних тестів

| # | Сценарій | Очікуваний результат |
|---|---|---|
| 1 | Перший запуск програми (Desktop) | Сплеш БД → майстер: власник → точка → каса → готово |
| 2 | Повторний запуск після налаштування | Звичайний екран входу, без майстра |
| 3 | Перший запуск клієнта (Сервер B) | Екран «Адреса сервера» → перевірка → майстер/вхід |
| 4 | Власник створює касира | Касир входить і бачить тільки свою точку |
| 5 | Касир входить | POS своєї точки, без switcher, без «Каси» |
| 6 | Власник перемикає точку | Дані сторінки — нової точки, < 1 сек |
| 7 | Касир шукає товар у sidebar «Наявність в інших точках» | Таблиця точок: ціна + залишок, read-only |
| 8 | Власник робить внесення 200 грн | Баланс каси +200, запис в історії |
| 9 | Власник інкасує 12 000 грн | Баланс −12 000, акт інкасації з № сумки |
| 10 | Власник інкасує більше балансу | Блокування + «Недостатньо готівки» |
| 11 | Касир намагається викликати API інкасації | 403 Forbidden |
| 12 | Офлайн-продажі синхронізуються | Чеки — у точку продажу, без змішування |
| 13 | Міграція існуючої інсталяції | Всі дані → «Основна точка», адміни → owner, майстер не показується |
| 14 | Оновлення версії з новими міграціями | Авто-міграції при старті, дані збережені |
