## 1. Дворівнева модель зберігання

| Рівень | Де | Формат | Роль |
|--------|----|--------|------|
| **Серверна БД (PostgreSQL)** | БД власника (одна на власника, database-per-tenant) | schema.sql | Єдине джерело істини (master): довідники, документи, продажі, мережа, ПРРО |
| **Мета-БД (PostgreSQL, public)** | `owners_db`, сітка кластера | schema.sql (Частина 2/3) | Реєстр БД власників; у ній також живуть мережеві таблиці `devices`, `store_activation_codes`, `audit_log`, `store_sync_state`, `store_product_prices` |
| **Offline-БД (SQLite)** | `~/.local/share/torgashka/offline.db` (на кожній касі) | 8 міграцій | Локальний кеш довідників + черга push транзакцій (outbox) + локальні залишки; синхронізується з сервером |
| **Embedded PostgreSQL** | single-store desktop | initdb-кластер у data dir застосунку | Повноцінна локальна PostgreSQL без встановлення сервера |

Архітектурний вибір (offline-first гібрид) обґрунтовано в
`sources/database-architecture-decision.md` (§A3 + B3). Продаж **не може
зупинитись** через відсутність інтернету (ПРРО дозволяє офлайн до 168 год).

## 4. Обмеження, індекси, ключі

**PK:** всі таблиці мають PK; `stock` — композитний `(store_id, product_id)`;
`user_stores` — `(user_id, store_id)`; `store_activation_codes` і
`store_sync_state` — PK = `store_id`; `owners_db` — PK `owner_id`.

**UNIQUE:**
- `users.login`, `write_off_reasons.name`, `store_activation_codes.code`,
  `store_product_prices(store_id, product_id)`, `print_templates(type, store_id) WHERE is_default`,
  `devices(store_id) WHERE source='legacy_migration'` (ідемпотентність міграції legacy).

**FK-правила:**
- Документи → `created_by_id → users(id) ON DELETE RESTRICT` (не можна видалити
  користувача з документами).
- Документи → `supplier_id → suppliers ON DELETE RESTRICT`.
- items → заголовний документ: `ON DELETE CASCADE`.
- items/product → `products(id) ON DELETE RESTRICT` (не можна видалити товар,
  що фігурує в документах).
- store_id → stores: `ON DELETE CASCADE` (архівація/видалення точки тягне її дані).
- debtor_payments/product_images/категорії parent: CASCADE / SET NULL відповідно.

**Індекси (типові патерни):**
- `ix_<table>_store_created (store_id, created_at)` — звіти/стрічки по точці.
- `ix_<table>_product_id`, `ix_<table>_<parent>_id` — FK-обходи.
- `ix_users_login` UNIQUE, `ix_user_stores_store/role`, `ix_audit_log_store_id_created_at`.
- GIN trigram-індекс на текстові поля (title/name) для нечіткого пошуку
  (реалізовано в Alembic-історії; legacy-еталон).
- number-індекси (`ix_invoices_number`, `ix_transfers_number`…) для унікальності номерів.

## 5. Row-Level Security (RLS) — другий контур ізоляції точок

**Мета:** навіть якщо SQL забуде `WHERE store_id=…`, PostgreSQL не віддасть
рядки чужої точки.

**Вмикається на всіх бізнес-таблицях зі store_id:**
```sql
ALTER TABLE <table> ENABLE ROW LEVEL SECURITY;
CREATE POLICY <table>_store_isolation ON <table>
  USING (
    store_id = NULLIF(current_setting('app.store_id', true), '')::uuid
    OR store_id IN (
      SELECT store_id FROM user_stores
      WHERE user_id = NULLIF(current_setting('app.user_id', true), '')::uuid
    )
  )
  WITH CHECK (…той самий вираз…);
```

Особливість: **owner бачить усі свої точки** (через JOIN `user_stores`),
тому для owner-запитів (звіти мережі, міжточкова наявність) політика
пропускає рядки всіх точок користувача. `user_stores` має політику
`user_stores_self` (user бачить лише свої прив'язки).

**Контекст проставляється застосунком** (не користувачем):
- `StoreCtx { user_id (JWT sub), store_id (X-Store-Id), role }` — `tokio::task_local!`.
- `StorePool` (обгортка `sqlx::PgPool`):
  - `begin()` → транзакція + `set_config('app.user_id'|'app.store_id', …, true)`
    (is_local=true — живе до commit/rollback);
  - одиночні запити через `Executor for &StorePool` → окреме з'єднання:
    set_config(is_local=false) → запит → **reset** (`set_config(..., NULL, false)`),
    щоб контекст не протікав у пул.
- NULLIF-обгортка обов'язкова: після reset `current_setting(..., true)` дає `''`,
  а не NULL — всі споживачі трактують `''` як NULL.

Повний механізм із кодом: `…/torgashka-infrastructure/src/store_ctx.rs`;
дизайн: `sources/multi-store-and-cash-operations.md §3.4.3`.

**Відомий статус (на момент звірки):** RLS-політики є, `ENABLE ROW LEVEL
SECURITY` є. Форсування для ролі застосунку (`FORCE ROW LEVEL SECURITY` +
підключення під непривілейованою роллю `torgashka_app`, а не власником
таблиць) — затверджено планом етапу 7 (`sources/database-architecture-implementation-plan.md`).

## 6. Ролі, provisioning, database-per-owner

- **Роль застосунку:** `APP_ROLE = "torgashka_app"` (константа в
  `provision.rs:33`). `provision_database(ProvisionTarget)` створює БД власника,
  роль, права, застосовує schema.sql. Є `cleanup_provisioned_database`.
- **Клієнтська провізія:** `admin_db_sources` (API `/api/v1/admin/db-sources/*`):
  `create_source → test_source → provision_source → activate_source`;
  статус у `db_sources.toml` прикладу: `provisioned_pending_activation`.
- **Персональна БД власника:** `owners_db(owner_id, db_name)` у мета-БД;
  `POST /api/v1/setup` (публічний) створює першого власника + його точку + БД.
- **Паролі користувачів:** bcrypt-хesh у `password_hash`/`pin_code`;
  **токени пристроїв:** у БД лише SHA-256-хеш (`devices.device_token_hash`);
  сирий токен повертається один раз при активації.
- **Паролі джерел БД** (`db_sources.toml`): `password_encrypted` (шифротекст,
  ключ у `.dbkey`/майстер-ключ застосунку).

## 7. Offline-БД (SQLite) — повна схема

Файл: `~/.local/share/torgashka/offline.db` (у dev-оточенні реально створюється;
`~/.local/share/torgashka/offline.db` ~18 МБ). Міграції: `offline/migrations/offline/0001…0008`.

### 7.1 0001 — baseline (legacy-сумісність)
```sql
products(id TEXT PK, data JSON, store_id, updated_at)      -- legacy JSON-кеш
receipts(id INTEGER PK AUTOINC, data JSON, store_id, synced 0/1, created_at)
settings(key PK, value, updated_at)
-- + індекси idx_receipts_synced, idx_products_*, idx_receipts_store
```
⚠️ `ALTER TABLE ADD COLUMN IF NOT EXISTS` у SQLite не працює — store_id для
legacy-БД додає Rust-крок `legacy_add_store_id` (PRAGMA table_info → ALTER).

### 7.2 0002 — sync_meta + outbox (синхронізація)
```sql
sync_meta(entity TEXT PK, version INTEGER)      -- остання версія довідника
outbox(id PK AUTOINC, type, client_uuid TEXT NOT NULL UNIQUE, payload JSON,
       status CHECK(pending|in_flight|failed|done), attempts, next_attempt_at,
       last_error, created_at, pushed_at)
-- idx_outbox_status(status,next_attempt_at), idx_outbox_created
```
`client_uuid` — UUIDv4 каси: **ключ ідемпотентності push** (сервер приймає
агрегат один раз; дублікат → `already_exists`, не помилка).

### 7.3 0003 — master_tables (нормалізовані копії довідників сервера)
```sql
categories(id TEXT PK, name, parent_id, is_deleted, server_version, data)
suppliers(id TEXT PK, name, phone, is_deleted, server_version, data)
employees(id TEXT PK, name, pin_hash, role, is_deleted, server_version, data)
stock_norms(product_id TEXT PK, min_qty, max_qty, is_deleted, server_version, data)
products_v2(id TEXT PK, …, data)   -- каталог для pull (замість legacy JSON-кешу products)
```
Правила: soft-delete (`is_deleted`), `server_version` = версія дельти, з якою
прийшов рядок; `data` — повний JSON payload.

### 7.4 0004 — ідемпотентність транзакцій
`ALTER TABLE receipts ADD COLUMN client_uuid TEXT;`
`CREATE UNIQUE INDEX idx_receipts_client_uuid ON receipts(client_uuid);`
(NULLABLE на рівні схеми: legacy-чеки без client_uuid не блокуються; нові чеки
завжди з UUIDv4 — гарантує застосунок.)

### 7.5 0005 — локальні залишки
`stock(product_id, qty, …)`, `local_stock`-логіка — каса знає свій залишок
офлайн (мінімальний поріг, перевірка quantity ≥ qty атомарно на сервері).

### 7.6 0006 — transaction_tables (агрегати нових операцій)
```sql
receipt_items(receipt_client_uuid, product_id, qty, price, …)
purchase_orders / inventories / transfers / write_offs / debtors_ledger / cash_ledger
-- спільний патерн: id INTEGER PK AUTOINC, client_uuid TEXT UNIQUE,
--   store_id TEXT, data JSON, synced 0/1, created_at; idx_*_synced
```

### 7.7 0007 — неймспейс локальних налаштувань
DDL немає (лише версія user_version=7). Конвенція:
- `local.*` — локальні ключі каси (ніколи не перезаписуються pull, не йдуть на сервер);
- без префікса — синхронізовані/конфігураційні (server_url, api_token, store_id).

### 7.8 0008 — sync_log (локальний журнал синхронізації)
```sql
sync_log(id PK, ts, kind CHECK(push_ok|push_fail|pull_ok|pull_fail|retry),
         entity, detail, attempts); idx_sync_log_kind_ts
```

### 7.9 Версіонування
`PRAGMA user_version` просувається міграціями (migrations.rs); порядок —
0001→0008, транзакційно, з Rust-кроком для legacy store_id.

## 8. Протокол синхронізації (коротко; повний дизайн — `sources/sync-schema-design.md`)

- **Pull довідників:** `GET /api/v1/sync/master?entity={categories|products|stock_norms|suppliers|employees|settings}&since_version=N`.
  Сервер повертає зміни з `server_version > N` (append-only дельти; BEFORE-тригер
  ставить `server_version = sync_meta.version` на момент зміни), `to` (нова
  версія) та `has_more`. Клієнт повторює pull, поки не наздожене. Обмеження
  розміру дельти.
- **Push транзакцій:** `POST /api/v1/sync/push` — каса відправляє агрегати з
  outbox (чек/повернення/замовлення/інвентаризація/переміщення/списання/
  борг/каса) з `client_uuid`. Сервер: ідемпотентний прийом
  (created | already_exists), атомарність транзакції + її ефекти
  (залишки, ledger, cash). Retry з exponential backoff; 5xx/429 → відкласти.
- **Конфліктів немає за конструкцією**: одна точка пише свої транзакції;
  залишок списується атомарним `UPDATE … WHERE quantity >= qty` на сервері.
- **Серверний стан точки:** `store_sync_state(store_id, last_synced_at, last_local_seq, status)`
  — аудит/SLA прийому; локальний `sync_log` — діагностика каси.
